# 화면 설계 작업지침

**2026-10-01 최우선 디자인 기준:** [최우선 디자인·UI·UX 지침](../generation2/docs/design-ui-ux-priority.md)을 먼저 적용합니다. 기존 Notion 중심 표현은 그 아래 보완 참고이며 이 문서는 과업의 입력/저장/취소/복귀·불편 예방·상태 설계 절차를 연결합니다. 현재 사용자 요청과 보존/권한/작업 순서 계약은 유지합니다.

**2026-09-30 작업 순서 정정:** [작업 진행과 검증 정책](작업%20진행과%20검증%20정책.md)을 따릅니다. 초안을 먼저 제시하고 검사는 변경·위험·실사용 단계에 맞게 선택합니다. 이 문서의 검사·완료 항목은 모든 초안의 선행조건이 아닙니다.

채택일: 2026-09-30. 적용 대상: 현재 학습 입력 웹앱에서 허용된 화면 설계·수정·구현·검수.

**사용자가 불편을 겪기 전에, 예상되는 혼란·불필요한 조작·입력 손실을 설계 단계에서 찾아 예방합니다.** 사용자의 “이걸 지침에 적극반영해야 하지 않겠는가?” 요청으로 첨부 작업지침과 용어사전을 채택했으며, “애초에 내가 불편을 느끼지 않도록 설계 지침 단계에서 서술해두면 되는거 아니야?”라는 후속 정정에 따라 예방을 기본 책임으로 명시합니다. 사용자 피드백은 예방 기준을 보완하는 근거이며 작업을 시작하기 위한 필수 조건이 아닙니다.

## 1. 채택 범위와 기존 기준

- 2026-10-01 사용자 결정에 따라 [제품 품질 기준](웹앱%20제품%20품질%20기준.md) Q01–Q15를 함께 적용합니다. 이미 완료/배포한 화면과 앞으로의 작업 모두 대상이며 내용 조합·편집·검색·이동/복귀·누적 대응·저장/복구·권한까지 연결된 실제 흐름으로 판단합니다. 관련 기존 경로를 재평가하고 필수 누락을 보완하며, 작은 수정마다 전수 QA를 요구하지 않습니다.
- 2026-09-30 사용자의 확대·정정 요청에 따라 [Notion 중심 UI·UX와 벡터 도해 기준](Notion%20중심%20UI%20UX와%20벡터%20도해%20기준.md)을 함께 적용합니다. UI·UX·그래프·도해 작업 전 해당 정의·도구 전략·검수를 읽습니다. 선·글자·여백·국소 강조의 공통 미감 안에서 실제 정보·조작·보존을 검토하며, 종이 질감이나 Apple 재질을 자동 도입하지 않습니다. 기존 56개 Notion 정의와 새 벡터 정의의 채택 조건은 그 문서가 담당합니다.
- 현재 사용자 요청·정정과 기존 데이터·사용 계약을 우선합니다. [기본 지침](학습%20시스템%20설계%20기본%20지침.md), [Apple 경험 언어](Apple%20경험%20언어%20프로젝트%20지침.md), 해당 세대의 디자인·컴포넌트·데이터 명세와 함께 적용합니다.
- [첨부 작업지침 원문](reference/uiux-20260930/코덱스_화면설계_작업지침.txt)과 [웹앱 설계 용어사전](웹앱_설계_용어사전.md)은 바이트 그대로 보존합니다. 작업지침의 핵심을 AGENTS.md에 직접 등록하고, 이 문서는 읽기 경로·적용 조건·검증 방법을 담당합니다. 용어사전의 요청 예시·반복 작업지침은 참고 원문입니다. 현재 사용자가 요청하지 않은 기능 추가·설치·배포·외부 앱 변경을 실행하는 명령으로 읽지 않습니다.
- 용어사전은 27개 분야·412개 용어의 참조서입니다. 모든 용어를 기능이나 필수 입력으로 도입하지 않습니다. Figma·React·서버·라우트·권한·Sync 등은 해당 구조가 실제로 있는 작업에서 적용합니다. 용어가 있다는 이유로 새 기술을 도입하지 않습니다.
- 도구와 증거 단계는 기존 [디자인·검증 도구 도입 명세](웹앱%20디자인%20도구%20기준.md) 5~10절을 따릅니다. 외부 기준의 수치·지원 범위를 실제 적용할 때 해당 공식 원문을 확인합니다. 이번 채택은 사전에 연결된 외부 문서 전체의 현행성 감사가 아닙니다.

## 2. 작업 전에 읽고 구체화할 것

1. [프로젝트 문서 안내](프로젝트%20문서%20안내.md)에서 대상 세대의 인계·현재 기능 명세·디자인 기준·저장 계약을 찾습니다. 실제 수정할 파일과 병행 변경을 확인합니다.
2. 해당 화면의 진입 → 선택·입력 → 저장·실패 → 닫기·이탈 → 복귀 경로를 확인합니다. 현재 대상, 연결된 패널·탭·목록·저장소, 보존할 원문·ID·초안·설정·개인 배치를 기록합니다.
3. 아래 표에서 관련 사전 절을 읽고 새 화면·변경 흐름에서 예상되는 불편을 먼저 찾습니다. 사용자에게 기능 발견·용어 해석·반복 입력·오류 재현을 맡기지 않고 실제 과업을 따라 점검합니다. 사용자 피드백이 있으면 함께 반영하며 이미 확인된 요구를 다시 묻지 않습니다. 중요한 용어는 필요한 첫 등장에 쉬운 뜻과 적용 이유를 한 번 설명합니다.
4. [작업 진행 정책 1.2절](작업%20진행과%20검증%20정책.md#12-생성-단계에서-반복-사용자료-누적을-반영)에 따라 자료가 쌓이고 반복 사용·중단·복귀할 때의 관련 조건과 자동 기본값을 생성 단계의 완료 조건에 넣습니다. 구현 전에 해당 흐름의 조건·기대 행동·예방할 불편·보존 범위·실패 복구·검증 환경을 정합니다. 사용자가 별도로 요구하지 않은 통상적인 사용성 기준도 허용된 범위에서 적용합니다. 기존 작업표·검증 기록이 있으면 재사용하며 작은 수정에 전체 문서나 상태표 작성을 강제하지 않습니다.

### 설계 단계에서 먼저 정할 예방 기준

아래 기준은 사용자의 불편 신고 여부와 관계없이 새 화면·변경 흐름에 적용합니다. 작업 범위와 실제 사용 환경에 해당하는 항목을 검토하고 기존 명세에 필요한 행동·조건을 남깁니다.

| 예상되는 불편 | 설계에 미리 정할 행동·조건 |
|---|---|
| 무엇을 누르고 어디에 기록할지 모름 | 현재 위치·대상·실제 다음 행동이 보이게 하고, 같은 행동은 같은 이름·위치·공통 요소로 표현합니다. 버튼의 결과와 저장 범위를 예상할 수 있게 합니다. |
| 이미 아는 값을 다시 입력하거나 선택할 내용을 기억해야 함 | 수정 가능한 기존 값과 관련 선택지를 제시하고, 여러 주제의 한 화면 입력·선택 입력을 유지하며 불필요한 단계·필수 입력을 추가하지 않습니다. |
| 입력 도중 글자·커서가 사라지거나 Enter로 잘못 저장됨 | 한글 조합·텍스트 선택·커서·포커스를 유지하고, 자동저장·집계·재조회가 편집을 끊지 않게 합니다. 조합 확정과 제출을 구별합니다. |
| 닫기·뒤로 가기 뒤 보던 목록과 입력을 다시 찾아야 함 | 진입·이탈·복귀별 선택·탭·필터·검색어·스크롤·초안의 유지 범위를 정하고 복원합니다. 닫기·취소·삭제의 결과를 구별합니다. |
| 저장 여부를 모르거나 실패·반복 클릭으로 기록이 손상됨 | 실제 저장 대상의 처리 상태·실패·초안 보존·재시도를 명세하고, 빠른 전환의 오래된 응답과 중복 요청을 처리합니다. |
| 작은 영역·긴 한글·키보드 때문에 읽거나 조작할 수 없음 | 실제 내용 폭·확대·좁은 높이·가상 키보드에서 배치·줄바꿈·스크롤·조작 위치·포커스를 유지하며 키보드와 드래그 대안을 마련합니다. |
| 갱신 뒤 개인 배치가 바뀌거나 같은 요소가 화면마다 다름 | 공통 토큰·컴포넌트를 재사용하고 개인 Canvas 좌표·연결·설정을 보존합니다. 저장된 개인 Canvas의 자동 배치는 명시적으로 실행한 범위에 적용합니다. 자동 계산을 기본으로 하는 탐색 그래프는 재계산 조건과 수동 위치 보존을 따로 정합니다. |

초안에서는 이번 핵심 흐름과 직접 연결된 보존·복구 조건부터 정하고 먼저 보여줍니다. 실제 사용에 적용하기 전에는 그 변경의 필수 경로를 확인합니다. 추가 상태·기기·실패 조합은 영향과 발견된 문제에 맞춰 후속 안정화에서 다룹니다. 미완인 조건을 표시하며 문서 등록만으로 실제 동작이 검증됐다고 처리하지 않습니다.

## 3. 행동과 상태의 적용 규칙

로딩·전환·이동·스크롤·터치의 구체적인 기본 동작은 [6절](#6-로딩전환이동스크롤터치의-상황별-기준)에 따릅니다. 화면별 예외는 해당 기능 명세에 이유와 보존 범위를 남깁니다.

### 탐색과 공통 컴포넌트

현재 위치와 편집 대상을 식별할 수 있게 합니다. ‘뒤로 가기’는 방문 이력 복귀, ‘상위로 가기’는 데이터의 부모 계층 이동으로 구별합니다. 복귀 시 선택·탭·검색어·필터·스크롤 중 이어서 작업하는 데 필요한 범위를 복원합니다. URL 탐색이 있는 웹앱에서는 직접 진입과 방문 이력이 없는 경우의 복귀도 정의합니다. 자유 글·비공개 입력·초안을 URL로 보내지 않습니다.

반복 요소는 기존 공통 컴포넌트와 색·글꼴·여백·곡률 토큰을 사용합니다. 형태의 변형, 포커스·로딩 같은 상태, 테마, 콘텐츠 슬롯을 구별하고 작은 요소를 조합합니다. 서로 다른 의미의 동작을 거대한 조건문 컴포넌트 하나로 억지로 합치지 않습니다. 재사용 구조화는 실제 반복과 변경 범위에 맞추며 작은 수정에서 전체 아키텍처를 교체하지 않습니다.

### 입력과 상태

Canvas는 데이터의 부모·자식 관계, 노드 좌표·크기·연결선, 뷰포트 이동·확대를 분리합니다. 갱신·화면 맞춤을 이유로 개인 배치를 초기화하지 않습니다. 저장된 개인 Canvas는 사용자가 명시적으로 자동 배치를 실행한 범위에서 필요한 좌표를 계산합니다. 원문/저장 좌표를 바꾸지 않는 탐색 그래프는 자료·영역 변화에 따른 자동 배치를 기본으로 제공하되 현재 수동 위치·선택·조작을 보존합니다. 기존 연결·메타데이터·사용자 글을 함께 보존합니다.

## 5. 펜으로 표시한 영역과 불편·불안 피드백 해석

### 5.1 불편·불안을 같은 피드백 신호로 받기

**'불편하다'와 '불안하다'는 모두 표시한 화면이 마음에 걸리거나, 어색하거나, 거슬리거나, 쓰기 어렵다는 넓은 피드백 신호로 받습니다.** 어느 단어를 썼는지로 원인 후보를 제한하거나 '불편=조작, 불안=저장/위험'으로 나누지 않습니다. 의미 차이를 사용자에게 묻지 않으며, 표시한 위치·실제 화면·주변 요소의 관계·작업 맥락에서 어시스턴트가 구체적인 원인을 해석합니다.

해석할 원인에는 읽기·판단·조작·입력·흐름의 부담, 밀도·정렬·여백·미감의 어색함, 행동 결과·적용 범위·자료 보존·복구의 불확실이 모두 포함됩니다. 실제로 조작에 실패하지 않아도 빽빽함·헐거움·불균형·낯선 표현·거슬리는 움직임·과한 장식이 문제일 수 있습니다. 취향이나 미감에 관한 느낌도 수정의 유효한 근거이며 사용자가 기능적 결함을 증명해야만 받아들이지 않습니다.

한 영역에 여러 원인이 함께 있을 수 있습니다. 사용자가 말한 느낌은 그대로 보존하되, 원인 설명은 근거에 따른 가설로 다룹니다. 아래 두 표는 같은 원인 후보 목록을 부담·배치·흐름과 결과·상태·통제의 관점으로 나눠 둔 참조입니다. 사용자의 표현을 두 종류로 분류하거나 매번 모두 검사하는 목록이 아닙니다.

| 학습 의미·평가 부담 | 체크하면 완전 이해로 기록되나, 빈칸이 실패인가, 모두 해야 하나 | 시도/저장/독립 수행/목표 달성 혼동·의무처럼 보이는 추천·압박 문구. 체크의 뜻·선택 입력을 유지하고 미입력을 실패나 0점으로 바꾸지 않습니다. |

### 5.4 펜 표시를 읽는 규칙

- **펜으로 표시한 곳에는 불편·불안이 있다는 것을 기본 의미로 적용합니다.** 사용자의 2026-09-30 명시 결정입니다. 별도의 '불편' 문구가 없어도 피드백이며, 원·밑줄·체크 모양·화살표·음영 등의 표시를 긍정·승인이나 단순 관심으로 읽지 않습니다. 문제의 원인·해결 방식·삭제/이동 권한은 표시만으로 확정하지 않고 화면과 맥락에서 해석합니다. 이후 사용자가 다른 뜻을 명시하면 그 설명을 우선합니다.
- 이미지·화면·표시를 실제로 확인합니다. 표시된 영역의 글·버튼·빈 공간·경계와 인접한 라벨/대상을 함께 읽습니다. 화면만으로 실제 클릭 결과·저장·복구·기기 동작을 확정하지 않습니다. 표시가 내용을 가리거나 자료를 열 수 없으면 확인한 범위와 필요한 부분만 밝히며 보이지 않는 내용을 만들지 않습니다.
- 원·밑줄·음영은 불편이 있는 위치, 화살표는 불편과 관련된 위치/흐름의 단서로 읽습니다. '여기로 옮겨'처럼 명시한 경우에만 이동 지시로 확정합니다. X·취소선만으로 기능/자료 삭제 권한을 추정하지 않습니다. 모든 펜 표시가 불편 신호라는 합의 외에 색이나 모양에 추가 의미를 임의 부여하지 않습니다.
- 여러 표시와 문구는 각각 대응시키고 누락하지 않습니다. 넓은 표시를 내부 요소 전체의 불만으로 단정하지 않습니다. 문제의 위치와 원인의 위치는 다를 수 있으므로, 필요한 인접 관계만 함께 살핍니다. 표시를 빌미로 전체 화면·모든 기기·QA 전수 검토로 확대하지 않습니다.
- 사용자의 표현을 그대로 보존하되 단어 선택에 고정된 원인을 부여하지 않습니다. '불안'이라고 했어도 배치·미감 문제를, '불편'이라고 했어도 저장·결과 문제를 맥락에 따라 해석할 수 있습니다. 사용자 성격·불안장애·학습 능력으로 설명하지 않습니다. 사용자가 원인을 정정하면 기존 가설을 갱신하고 이미 고친 내용을 반복해서 변호하지 않습니다.

### 5.5 해석에서 수정으로 이어가는 방식

1. **관찰과 가설을 나눕니다.** 표시한 위치와 보이는 사실을 짚고, 그 사실에 가장 잘 맞는 원인 가설 한두 개만 짧게 제시합니다. 사용자 감정 자체를 부정하거나 '실제 오류가 없으니 괜찮다'고 판정하지 않습니다. 분류표 전체나 UX 강의를 먼저 늘어놓지 않습니다.
2. **필요한 경우만 묻습니다.** 근거 있는 보수적 수정이 가능하면 해석을 밝히고 국소 시안으로 보여줍니다. 서로 반대되는 수정이 필요하거나 필수 정보가 없으면 해결 방향을 가르는 짧은 질문 하나를 합니다. '어떻게 불편한지 자세히 설명해 달라'는 요구나 분류 선택을 기본 절차로 만들지 않습니다. 질문 중에도 독립적으로 가능한 시안 작업은 이어갑니다.
3. **원인에 맞는 작은 변경을 합니다.** 사용자가 볼 수 있는 수정과 직접 완료 조건을 먼저 좁힙니다. 불안을 줄이려고 실제 보존 없이 안심 문구를 추가하거나, 불편을 줄이려고 기능·자유 글·선택 입력·설정·ID·이력·Canvas 배치를 삭제하지 않습니다. 시안 피드백은 시안 수정으로 먼저 대응하며, 제품 적용·배포·외부 변경에는 기존 대상별 허용·보류를 유지합니다.
4. **같은 위치에서 결과를 보여줍니다.** 표시했던 영역의 무엇이 어떻게 달라졌고 어떤 부담을 줄이려는지 짧게 설명합니다. 읽기/배치 문제는 해당 화면, 입력/저장 문제는 직접 관련 동작만 확인합니다. 원래 이미지·표현과 중요한 미확정 해석/정정은 해당 작업의 기존 인계나 결과에 필요한 만큼 남기며 새 감사·점수표·피드백 DB를 자동 생성하지 않습니다. 사용자가 다시 판단할 수 있게 하되 사소한 변경마다 승인을 요구하지 않습니다.
5. **느낌의 해소를 대신 판정하지 않습니다.** '간격을 조정했고 해당 폭에서 겹치지 않는다'는 구현 확인과 '민석님이 편해졌다·안심한다'는 사용자 경험을 구별합니다. 실제 피드백이 없으면 후자를 완료로 주장하지 않습니다. 새로운 피드백이나 실패 근거 없이 같은 검사·수정을 반복하지 않습니다.

예시 응답: '표시한 아래쪽 버튼이 입력 영역과 멀리 떨어져 있어, 어느 내용에 적용되는지 확신하기 어려운 것으로 읽었습니다. 버튼을 해당 입력과 묶고 적용 대상을 짧게 보이도록 시안을 바꾸겠습니다.' 이는 가상 예시이며 실제 사용자 감정·의도·결함의 확인 기록이 아닙니다.


## 6. 로딩·전환·이동·스크롤·터치의 상황별 기준

2026-10-01 사용자 요청으로 기존 원칙을 실제 행동과 확인 기준에 연결합니다. 모든 항목을 매번 검사하는 목록이 아니라, 생성·수정하는 흐름에 해당하는 기본 계약입니다. 기능을 삭제하거나 필수 입력을 늘리지 않으며 원문·ID·이력·초안·선택·사용자 설정·개인 배치를 보존합니다.

### 6.1. 채택 근거와 적용 경계

2026-10-01 사용자 후속 결정: VoiceOver 전용 구현·설정·검증은 이번 UX 작업에서 제외합니다. 일반 키보드·터치·확대·초점·저장/복귀 기준은 유지하며, VoiceOver를 완료·배포의 잔여 조건으로 요구하지 않습니다.

- **접근성 표준:** [WCAG 2.2](https://www.w3.org/TR/WCAG22/)의 키보드(2.1.1/2.1.2), 초점 순서·표시·가림(2.4.3/2.4.7/2.4.11), 제스처·포인터 취소·드래그 대안·대상 크기(2.5.1/2.5.2/2.5.7/2.5.8), 상태 메시지(4.1.3)를 관련 흐름에 적용합니다. AA 대상 크기24×24 CSS px의 간격·인라인 등 예외와 프로젝트의 더 여유 있는44/48px 기본값을 구별합니다. 상호작용 애니메이션 감소(2.3.3)는 AAA 항목이지만 현재 제품 기본값으로 채택합니다. 일부 항목 적용을 전체 WCAG 준수로 보고하지 않습니다.
- **컴포넌트 작업 관행:** [WAI-ARIA APG 모달 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)의 배경 비활성, 내부 Tab 순환, Escape, 진입·복귀 초점을 재사용합니다. APG는 구현 지침이며 별도의 적합성 인증이나 WCAG 표준 자체가 아닙니다.
- **플랫폼 설계 권고:** Apple HIG의 [로딩](https://developer.apple.com/design/human-interface-guidelines/loading), [모션](https://developer.apple.com/design/human-interface-guidelines/motion), [제스처](https://developer.apple.com/design/human-interface-guidelines/gestures)를 참고합니다. 브라우저·OS의 익숙한 조작을 우선하며 네이티브 전용 API나 효과를 웹에 그대로 강제하지 않습니다.
- **웹 성능 권고:** [Core Web Vitals](https://web.dev/articles/vitals)의 LCP≤2.5초, INP≤200ms, CLS≤0.1을 측정 목표로 사용합니다. 모바일·데스크톱별 실제 방문75백분위 기준이며 한 번의 개발 화면 검사·Lighthouse 점수를 전체 사용자 성능으로 확대하지 않습니다. INP는 서버 작업 완료 시간이 아니고 이 지표는 스크롤 감각·학습 효과를 보증하지 않습니다.
- **브라우저 기능:** [Pointer Events](https://www.w3.org/TR/pointerevents3/), [CSS Overscroll Behavior](https://www.w3.org/TR/css-overscroll-1/), [CSS Overflow의 scrollbar-gutter](https://www.w3.org/TR/css-overflow-3/#scrollbar-gutter-property), [Visual Viewport](https://drafts.csswg.org/cssom-view/#the-visualviewport-interface)를 실제 지원 범위에서 재사용합니다. 기본 HTML/CSS·현재 공통 UI로 부족한 부분만 구현합니다.

기존120ms 피드백·180ms 전환과44/48px 조작 크기는 프로젝트 설계값입니다. 보편적 법칙의 유일한 정답으로 표현하지 않으며 실제 조작·내용·기기에 따라 조정합니다.

### 6.2. 로딩·대기·갱신

- 첫 진입, 화면 코드 지연 로딩, 목록 재조회, 기록 저장을 구별합니다. 로딩을 빈 목록이나 오류로 표시하지 않고 접근 가능한 상태 메시지를 제공합니다. 진행률·남은 시간은 실제로 계산할 수 있을 때만 표시합니다.
- 자료가 이미 표시돼 있으면 관련 영역의 갱신 상태를 알리고 원문·초안·선택·스크롤을 유지합니다. 전체 화면을 지워 재로딩하거나 입력을 무조건 막지 않습니다. 실행 중 같은 명령의 중복 실행은 막되 다른 이동·복구 행동은 실제 가능 범위에서 유지합니다.
- 짧은 작업에 불필요한 스피너 깜빡임·완료를 늦추는 최소 대기 시간을 넣지 않습니다. 스켈레톤은 예상 구조를 알고 있을 때만 쓰고 실제 결과와 영역 크기를 맞춥니다. 장식만을 위한 로딩 요소를 추가하지 않습니다.
- 지연이 길어지는 흐름에는 현재 단계와 실제 가능한 재시도·취소·이탈을 정합니다. 재시도는 같은 의도의 중복 기록을 만들지 않아야 합니다. 취소가 서버 효과까지 취소하지 못하면 그 범위를 정확히 안내합니다. 시간 초과 기준은 해당 API·작업 명세에 두고 모든 기능에 임의의 동일 시간을 강제하지 않습니다.
- 확인: 느린 응답·응답 순서 역전·실패·이탈 후 응답에서 잘못된 대상 표시, 원문 손실, 중복, 영구 대기 여부를 해당 변경 범위에서 관찰합니다.

### 6.3. 화면 전환·움직임·이동

- 새 과업으로 진입하면 제목·현재 대상·가능한 다음 행동을 식별할 수 있게 합니다. 뒤로/앞으로 복귀는 해당 과업의 선택·검색·필터·스크롤·초점을 이어줍니다. 직접 URL 진입과 방문 이력이 없는 경우에는 실제 상위/목록 경로를 제공합니다.
- 화면 전환의 초점·스크롤 복원은 늦게 로딩되는 본문이 준비된 뒤 완료합니다. 로딩 중 임시로 짧아진 화면에서 잘린 위치를 최종 위치로 저장하지 않습니다. 이미 입력·대화상자가 초점을 갖거나 사용자가 새로 조작했다면 자동 복원이 그 조작을 덮어쓰지 않습니다. 이전 화면의 늦은 복원은 다음 화면에 적용하지 않습니다.
- 이동 중 미저장 내용은 기존 초안·저장 정책으로 보존합니다. 실제 유실 가능성이 있을 때만 이탈 확인을 사용합니다. 모든 클릭에 확인창을 붙이지 않습니다. 자유 글·인증 정보·민감한 초안을 URL 또는 탐색 힌트에 넣지 않습니다.
- 움직임은 관계·상태 이해에 필요한 범위에서 기존 모션 토큰을 사용합니다. 감소 설정에서는 불필요한 이동·확대·자동 스크롤을 제거합니다. 애니메이션 완료를 저장 완료로 표현하거나 효과 때문에 입력·이동을 늦추지 않습니다.
- 확인: 정상 이동, 브라우저 뒤로/앞으로, 새로고침, 처음 여는 지연 화면, 빠른 연속 이동에서 대상·초점·위치·초안이 맞는지 관찰합니다.

### 6.4. 스크롤·자료 누적·팝업

- 본문, 독립 패널, 표/코드/Canvas 등 작업 영역의 스크롤 주체를 정합니다. 일반 읽기에서는 세로 흐름을 우선하고 가로 스크롤은 실제로 필요한 영역 안에 제한합니다. 기본 관성·휠·키보드·터치 스크롤을 불필요하게 가로채지 않습니다.
- 모달은 배경 조작·스크롤을 막고 내용은 내부에서 스크롤합니다. 안쪽 끝에서 배경으로 스크롤이 이어지지 않게 하며 닫으면 원래 위치와 초점으로 돌아갑니다. 스크롤바 출현/소멸 때문에 본문 폭이 튀지 않게 합니다. 여러 스크롤 영역에 overscroll 차단을 무조건 적용하지 않습니다.
- 긴 제목·목록·원문·확대·좁은 높이에서도 닫기와 다음 행동에 접근할 수 있어야 합니다. 콘텐츠를 잘라내거나 글자를 일괄 축소해 해결하지 않습니다. 화면 키보드에서는 실제 보이는 영역 안에 입력과 조작을 두되 확대·현재 입력을 임의 초기화하지 않습니다.
- 자료 갱신·항목 추가·이미지 로딩·가상 목록이 읽던 위치를 불필요하게 이동시키지 않아야 합니다. 추가 자료는 명시적 더 보기 또는 적합한 자동 로딩을 선택하고 끝·실패·재시도를 구별합니다. 무한 스크롤·가상화를 모든 목록의 기본으로 도입하지 않습니다.
- 확인: 긴 자료의 첫 부분·중간·끝, 팝업 내부/배경, 자료 갱신·복귀, 좁은 화면과 확대에서 넘침·초점 가림·스크롤 튐·조작 가능 여부를 관찰합니다.

### 6.5. 터치·클릭·드래그·제스처

- 버튼은 기본 click 활성화를 사용합니다. 손을 대는 순간 실행해야 할 구체적 이유가 없으면 pointerdown/mousedown에서 닫기·삭제·저장을 실행하지 않습니다. 손을 떼기 전 취소·대상 밖 이동·pointercancel이 실행으로 바뀌지 않아야 합니다.
- 모달 배경 닫기는 배경에서 시작하고 같은 배경에서 끝난 기본 클릭에만 적용합니다. 본문/입력에서 시작한 드래그·선택·스크롤이 배경에서 끝나거나, 배경에서 시작해 본문에서 끝난 경우 닫지 않습니다. Escape와 명시적 닫기 버튼을 유지합니다. 닫기 요청은 기존 초안 보존/차단 정책을 따릅니다.
- 실제 조작 영역은 기본 아이콘44px·주요 텍스트 버튼48px를 유지하고 긴 한국어에는 높이를 늘립니다. 인접 위험 행동의 간격·위치를 확인하고 아이콘만 있는 버튼에는 이름을 제공합니다. 중요 조작을 hover·길게 누르기·복잡한 제스처만으로 제공하지 않습니다.
- 스크롤·텍스트 선택·드래그·화면 이동·확대의 충돌을 구별합니다. touch-action:none은 필요한 직접 조작 영역으로 제한하고 페이지 전체의 확대를 막지 않습니다. 드래그에는 선택 후 이동·메뉴 등 실제 사용 가능한 대안을 제공합니다. 펜 입력의 손바닥 처리·물리 기기 동작은 별도 증거가 필요합니다.
- 확인: 클릭/키보드 활성화, 누른 뒤 취소/밖으로 이동, 연속 실행, 드래그/스크롤 충돌, 실제 표시 영역의 크기와 간격을 관련 조건에서 확인합니다. 마우스·합성 포인터 결과를 물리 터치 증거로 바꾸지 않습니다.

### 6.6. 입력·초점·중단·실패 복구

- 기존 한글 조합·캐럿·선택 방향·내부 스크롤을 유지합니다. 자동저장·재조회·집계·렌더링 때문에 재마운트하거나 사용자가 쓰는 값을 바꾸지 않습니다. 키보드 단축키는 조합 중 제출/닫기로 오인하지 않습니다.
- 모달 진입 시 내부의 적절한 요소로 초점을 옮기고 Tab/Shift+Tab을 내부에서 순환합니다. 닫을 때 아직 존재하고 사용 가능한 진입 요소로 스크롤 이동 없이 복귀합니다. 요소가 없어졌으면 현재 과업의 제목/다음 행동으로 돌아가며 숨은·비활성 요소에 초점을 보내지 않습니다.
- 정상 입력·긴 내용·누적 자료·중단/재접속·저장 실패 중 관련 조건을 선택합니다. 원문과 저장 의미는 기존 데이터 계약이 담당하고 공통 UX 요소는 임의 저장·완료·학습 성과 판정을 하지 않습니다.
- 복구 안내에는 실패 범위·남은 자료·가능한 다음 행동을 붙입니다. 필요한 실패를 사라지는 알림에만 두지 않으며 실행 취소를 읽기 전에 없애지 않습니다. 수정·취소·다시 열기·복귀는 명확한 행동명으로 제공합니다.

### 6.7. 적용·완료 기록

각 작업에서 적용한 조건과 수정 위치, 합성 검사/실제 브라우저/운영 서버/물리 기기의 증거를 구별합니다. 공통 컴포넌트 자동검사 통과를 모든 사용 화면의 완료로 확대하지 않습니다. 변경 관련 확인이 통과하면 전달하고 새 실패·변경·영향 없이 검사를 확대하지 않습니다. 이번 적용 현황과 실제 확인은 웹앱의 `docs/ux-interaction-audit-20261001.md`와 최신 인계에 남깁니다.

## 7. 작은 기능을 처음부터 끝까지 연결하며 설계하기

2026-10-01 사용자 요청으로 [와니(@designbywani)의 Instagram 릴스 Dc-4BErzhRJ](https://www.instagram.com/reel/Dc-4BErzhRJ/)의 조언을 현재 웹앱의 작업 기준으로 채택합니다. 확인한 자료는 게시자가 작성한 설명 본문 전체와 재생 화면에 표시된 검색 실패·다시 불러오기 예시입니다. 영상의 음성 전체를 전사·대조한 것은 아닙니다. 아래의 저장·보존·검증 연결은 기존 프로젝트 계약에 맞게 구체화한 적용 지침이며 영상의 직접 인용이 아닙니다.

### 7.1. 게시물의 뜻과 근거 수준

작성자는 비전공자로 디자인을 준비하면서 개별 화면을 모사할 때보다 작은 서비스의 전 과정을 직접 설계할 때 자신의 지식 공백을 더 많이 발견했다고 설명합니다. 그 과정에서 화면 사이의 연결, 컴포넌트의 속성·상태, 검색 결과 없음이나 오류의 안내를 고민하고, 필요한 내용을 공부해 실제 디자인에 적용하라고 권합니다. 이는 작성자의 경험에 근거한 실무 조언입니다. 모든 사람에게 가장 빠른 학습법이라는 비교 실험이나 효과가 검증된 법칙으로 취급하지 않습니다.

### 7.2. 현재 프로젝트에서 실행할 기준

1. **작업 단위를 사용자가 끝낼 수 있는 작은 과업으로 잡습니다.** 새 기능이나 큰 변경은 ‘주제를 찾아 공부 기록을 남기고 다시 열기’처럼 시작과 결과가 이어지는 단위로 나눕니다. 시작 상태·사용자 행동·저장 결과·복귀 조건을 기존 기능 명세에 짧게 정합니다. 앱 전체를 한 번에 완성하거나 별도 연습 서비스를 만드는 요구로 확대하지 않습니다. 작은 시각 수정은 해당 변경과 연결된 흐름만 확인합니다.
2. **화면의 연결을 실제 흐름에 반영합니다.** 진입 → 선택·입력 → 결과/저장 → 닫기·뒤로 가기 → 다시 열기에서 대상과 다음 행동이 이어지게 합니다. 중간 화면·버튼만 만들어 연결된 기능의 완료로 보고하지 않습니다. 의미 있는 첫 흐름을 먼저 보여주고, 허용된 범위의 프론트엔드·저장·서버 연결을 같은 작업에서 이어갑니다. 자세한 전환·실제 확인은 작업 진행 정책 9절과 2.1절을 따릅니다.
3. **컴포넌트의 속성과 상태를 함께 설계합니다.** 기존 공통 UI·토큰을 우선 재사용하며 입력값, 선택 여부, 읽기 전용, 로딩, 실패 등 해당 요소에 실제 필요한 조건과 가능한 행동을 정합니다. 변경에 관련된 상태를 기존 컴포넌트 계약이나 Storybook에 연결하고, 갱신 때문에 한글 조합·포커스·사용자 편집을 초기화하지 않습니다. 모든 요소의 모든 상태표를 작은 수정의 선행 산출물로 요구하지 않습니다.
4. **자료 없음·결과 없음·불러오기 실패를 구별합니다.** 최초 기록이 없는 상태에는 시작 행동을, 검색이 정상 완료됐지만 일치 항목이 없는 상태에는 검색어·필터 수정/해제를, 조회에 실패한 상태에는 실패 범위와 다시 불러오기를 제공합니다. 실패를 ‘결과 없음’으로 숨기거나 기록을 지우지 않습니다. 저장 실패에는 원문·초안 보존과 재시도를 연결합니다. 적용 가능한 취소·복귀·중단 후 재접속도 같은 흐름에서 다룹니다.
5. **만들며 드러난 지식 공백을 실제 수정으로 해결합니다.** 무엇을 모르는지 구체적인 막힘으로 좁힌 뒤 현재 채택 기준·공식 문서·적합한 기존 도구를 확인해 같은 기능에 적용합니다. 공부할 목록이나 도구 설치만 남기지 않습니다. 기존 기준 조사 → 구현 → 드러난 문제의 조사·수정 순서이며, 사전 조사를 생략하거나 관련 없는 장기 조사로 작업을 미루지 않습니다.
6. **반복 사용과 자료 증가에서도 과업이 이어지는지 확인합니다.** 변경과 직접 관련된 긴 한국어·자료 누적·좁은 화면·연속 편집·중단/재접속·실패/재시도를 골라 확인합니다. 자동 기본값과 재계산은 사용자 원문·ID·이력·초안·선택·개인 배치를 보존합니다. 체크를 숙달·독립 성공으로 추정하지 않습니다. 상세 반복 사용 기준은 작업 진행 정책 1.2절을 따릅니다.
7. **완료는 연결된 행동과 확인한 결과로 판단합니다.** 정상 과업과 중요한 예외/복귀 경로를 직접 조작하고 관련 저장 결과를 확인합니다. 구현·브라우저 조작·서버 적용·배포·물리 기기·학습 효과의 증거를 구별합니다. 기존 명세와 완료 보고에 이번 연결·확인·남은 조건을 짧게 남기며, 문서 추가·예쁜 화면·컴포넌트 검사만으로 전체 흐름의 완료를 주장하지 않습니다. 검사 시점·범위는 기존 작업 진행 정책을 유지합니다.

### 7.3. 재사용한 방법과 적용 한계

- [Storybook 공식 문서](https://storybook.js.org/docs/writing-stories)는 입력 속성에 따른 컴포넌트의 렌더 상태를 stories로 표현하는 방법을 설명합니다. 기존 도구에서 관련 상태를 비교하는 데 사용하며, 이를 전체 앱의 저장·권한·복귀 확인으로 확대하지 않습니다. 현재 패키지의 버전을 자동 변경하지 않습니다.
- [GOV.UK Design System의 오류 메시지 지침](https://design-system.service.gov.uk/components/error-message/)은 사용자가 고칠 수 있는 입력 오류와 서비스 문제를 구별하고, 무엇이 잘못됐고 어떻게 고칠지 안내하도록 권합니다. 오류 종류에 맞는 안내·복구 행동을 정할 때 참고하며, 영국 행정 서비스의 화면이나 문구를 그대로 복제하지 않습니다.
- 위 7개 실행 기준은 영상의 조언과 이미 채택한 프로젝트 계약을 연결한 사용자 채택 지침입니다. 새로운 과학 법칙·공식 표준으로 명명하지 않습니다. 지침 등록은 제품 개편·실제 사용 검증·공개 배포의 완료나 새 권한을 뜻하지 않습니다.
