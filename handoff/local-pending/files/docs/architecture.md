상태: 개발 기준 채택. 배포·온라인·오프라인 동작 검증은 별도 Phase이며 채택만으로 통과하지 않는다.

React + TypeScript + Vite를 사용한다. 과목/범위/초안/원기록 상태를 명시적으로 연결하고 공통 컴포넌트를 재사용하며, 현재 웹앱의 공통 상태·저장·브라우저 동작을 기준으로 구현한다. 별도 SSR 서버, Next.js, 자체 인증 서버는 필요하지 않다.

GitHub를 코드 기준으로 하고 GitHub Pages에 정적 app shell을 배포한다. 하위 저장소 경로를 Vite base로 지정하고 hash route로 직접 링크·새로고침을 지원한다. Auth callback의 허용 URL은 실제 배포 주소에 맞춘다. 현재 로컬 독립 Git에서 시작하며 원격 생성·배포 전까지 GitHub 완료로 표시하지 않는다.

Supabase PostgreSQL/Auth는 온라인 승인 데이터·조건부 쓰기·관계 무결성·사용자 소유권을 맡는다. 모든 사용자 행은 RLS 및 소속 FK로 보호한다. 프런트는 publishable key만 사용하며 service-role/secret을 포함하지 않는다. Realtime 알림은 변경 통지를 보조할 뿐 누락 없는 Sync 원장이 아니다.

IndexedDB는 온라인 기본 CRUD를 검증한 다음 추가한다. 캐시와 미전송 원본/초안/outbox를 구별하며, 로컬 엔터티 변경+outbox는 하나의 transaction으로 commit한다. PWA 서비스워커는 앱 껍데기만 관리하고 인증 응답/API를 무조건 캐시하지 않는다.

## 모듈 경계

- domain: ID, 범위, 계층, 실제 사건/기록, TRACE, 삭제/이력의 순수 명령과 검증.
- data: 먼저 demo 저장소, 다음 Supabase online adapter, 이후 IndexedDB/outbox adapter. UI는 저장 상태를 구별한다.
- ui: semantic token, 실제 공통 컴포넌트, 접근성·터치·키보드 상태.
- features: 홈·목차·기록·일정·조회. 한 번만 쓰는 화면은 억지 범용화하지 않는다.
- migration: 읽기 전용 parser → validation → preview → dry-run → import → integrity. 원본 수정 금지.

## 프론트엔드·백엔드 책임 분리

2026-09-30 사용자 요청에 따른 개발 지침입니다. 프론트엔드는 브라우저에서 실행되는 앱, 백엔드는 Supabase의 인증·DB·서버 측 처리를 뜻합니다. `domain`과 `data`라는 폴더 이름은 실행 위치를 뜻하지 않습니다. 현재 두 모듈도 브라우저에서 실행되며, 브라우저 저장·오프라인 큐는 클라이언트 책임입니다.

### 구현할 때 지킬 경계

- **화면 → 저장 인터페이스 → 저장 어댑터 → 저장소/서버**로 연결합니다. UI는 `DemoRepository`나 Supabase SDK의 구체적인 타입·응답에 직접 묶이지 않도록 정리합니다. 저장 인터페이스는 비동기 요청·실패를 표현할 수 있어야 하며, 기존 `data-contract.md`의 ID·namespace·명령·버전·중복 요청·이력·충돌 보존 조건을 유지합니다. 단순 CRUD로 필요한 의미를 지우지 않습니다.
- 기록·초안·복구 자료의 저장 접근은 해당 `data` 모듈로 모읍니다. 표시용 임시 UI 상태는 프론트엔드가 관리하되, 보존이 필요한 사용자 설정·배치에는 기존 저장 계약을 적용합니다. 저장 방식을 바꾸면서 기존 localStorage 키·자료·원문을 조용히 폐기하지 않습니다.
- 입력 중 안내와 빠른 검증은 클라이언트에서 수행합니다. 사용자 소유권·관계·조건부 쓰기·중복 요청의 최종 보장은 서버가 수행합니다. DB의 version 검사와 쓰기, 원문과 수정 이력의 반영은 서버에서 원자적으로 처리합니다. 브라우저의 `userId` 검사나 Web Lock을 서버 권한·다기기 충돌 보장으로 대체하지 않습니다.
- UI와 저장 연결 사이의 자료형·오류·저장 상태 계약을 유지합니다. 저장 요청 성공, 서버 반영, 상대 기기 수신을 구별하며, 충돌·응답 유실·세션 실패에서 원문과 재시도 근거를 보존합니다. 백엔드의 스키마·마이그레이션·RLS·서버 함수를 구현하면 재현 가능한 정의를 저장소에서 관리하고 비밀키·개인 자료는 포함하지 않습니다.
- 이 경계를 위해 별도 서버나 프론트·백 별도 저장소를 새로 만들 필요는 없습니다. 관련 기능을 구현·수정할 때 필요한 경계를 정리합니다. 작은 화면 수정 전에 전체 분리 작업·미래 Sync 구현·전체 QA를 강제하지 않으며, 구현 순서는 아래 기존 기준을 유지합니다.

### 현재 구현 상태와 확인 기준

아래는 실제 온라인 구현 이전의 지침 정리 시점 기록입니다. 현재 구현은 이 문서의 2026-09-30 실제 온라인 구현 절과 online-storage.md를 따릅니다. 당시 앱은 `src/App.tsx`에서 `new DemoRepository(localStorage)`를 만들고 `Workspace`도 그 구체적인 타입을 받습니다. 일부 화면·입력 코드의 브라우저 저장소 직접 접근이 남아 있습니다. `domain`·`data`·`ui`의 모듈 분리는 있으나, 공통 저장 인터페이스를 통한 연결과 실제 Supabase 온라인 어댑터는 아직 구현해야 합니다. 기존 인계의 Supabase 프로젝트 생성·Healthy 확인은 앱 Auth·서버 저장·RLS 동작 확인과 구별합니다.

분리 결과는 폴더 생성이나 문서 채택이 아니라 관련 코드의 의존관계로 확인합니다. 서버 기능은 해당 변경의 실제 인증·읽기/쓰기·권한 거부·버전/중복 요청 처리와 서버 반영 증거로 확인합니다. 프론트엔드, 로컬 저장, 백엔드, 동기화의 구현·검증 상태를 따로 보고하되, 전체 잔여 보고에서는 그 밖의 채택 기능도 누락하지 않습니다. 확인의 시점과 범위는 공통 작업 진행 정책을 따릅니다.
