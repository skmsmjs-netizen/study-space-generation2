## 1. 지위와 적용 범위

**이 대화에서 지정한 Instagram 자료 31개와 디자인 개념 8개를 프로젝트의 최우선 디자인·UI·UX 기준으로 채택한다. 현재 화면과 이후의 조사·설계·문서·도해·구현·수정·리뷰·유지보수에서 이 문서의 관련 기준을 먼저 적용한다. 중요한 정보와 다음 행동을 분명히 하고, 불필요한 선택·조작·장식을 줄이며, 공통 기초·구성 요소·상태·사용 흐름을 일관되게 연결한다.**

- 시스템·개발자 지침의 범위 안에서 현재 사용자 요청·정정이 먼저다. 프로젝트의 디자인 판단에서는 이 문서 → 기존 Notion·Apple·ChatGPT·Claude 미감 및 개별 디자인 참고 문서의 순서로 적용한다. 하위 경로의 오래된 외형 지침이나 예시 값이 이 우선순위를 낮추지 않는다.
- 이전 미감·기술 기준은 충돌하지 않는 부분을 계속 사용한다. Notion 스타일의 유지 자체를 새 기준 적용보다 우선하지 않는다. 기존 공통 UI와 토큰 체계를 재사용하되, 필요한 시각 값은 담당 원본에서 조정하고 관련 호출·테마·사용자 설정 영향을 확인한다.
- 원문·ID·초안·이력·개인 설정/배치, 학습 의미, 실제 저장/복구, 사용자별 서버 권한은 유지한다. 미니멀리즘·단계 축소를 이유로 필요한 기능·예외·보안 확인을 삭제하지 않는다.
- 사용자 결정으로 제외한 결제·문의 접수/회신·VoiceOver 전용 구현/검증을 예시에서 다시 도입하지 않는다. 일반 읽기·키보드·터치·확대 기준은 유지한다. AI 기능의 민석 전용 권한도 유지한다.
- 현재 기존 화면도 관련 변경·평가의 대상이다. 이번 지침 등록 자체를 전체 화면 재설계·검증·배포 완료로 보고하지 않는다. 지침 생성 요청을 새 외부 전송·계정 생성·결제·공개 배포 권한으로 확대하지 않는다.

## 3. 실제 화면과 사용 흐름의 필수 기준

### 3.1. 사용 목적·사용자 조사·첫 이용 — L05·L19·L21·L30

화면의 목적을 사용자가 끝낼 수 있는 과업으로 정의한다. 제품 전략·사용자 조사·정보 구조·사용자 흐름·와이어프레임·프로토타입·사용성 확인과, 색·글자·간격·배치·아이콘·버튼·시각 표현을 함께 다룬다. UI와 UX를 따로 완성했다고 보지 않는다.

- 실제 사용자의 필요·불편·현재 자료에서 설계한다. 디자인 전시 반응이나 제작자 취향만으로 제품 적합성을 판단하지 않는다.
- 첫 이용에서 현재 위치와 다음 작은 행동을 알 수 있게 한다. 목적에 필요 없는 가입 후 단계·재입력·선택·클릭을 줄이고 이미 알려진 값과 이어가기를 활용한다. 필요한 인증·승인·권한·저장 확인을 생략해 숫자만 줄이지 않는다.
- 분명한 탐색, 짧은 온보딩, 공통 디자인 시스템, 뚜렷한 위계, 과업별 주요 행동을 연결한다. 진행 중·완료·실패를 실제 상태로 표시한다.
- 게시물의 88%, 2.5/3.2/1.8배, 42/28/35/22%는 연구 조건과 측정 근거가 확인되지 않은 주장이다. 목표 수치·보장 효과·현재 앱 성과로 사용하지 않는다.

### 3.2. 정보 위계와 관계 — L01·L06·L07·L15·L20·L31

핵심 판단에 필요한 내용을 먼저 배치한다. 중요도는 글자 크기/굵기·위치·간격·대비로 표현하고 여러 요소를 같은 강도로 경쟁시키지 않는다.

- 위계: 무엇을 먼저 볼지 분명히 한다.
- 대비: 중요 요소와 상태를 구별한다.
- 정렬: 공통 기준선과 격자로 관계를 드러낸다.
- 근접성: 관련 요소를 가까이, 다른 묶음은 충분히 떨어뜨린다.
- 반복: 같은 역할의 표현을 재사용한다.
- 균형: 시각적 무게를 조절한다. 대칭을 필수로 삼지 않는다.
- 여백: 읽기와 집중, 묶음을 설명한다. 흰색이나 큰 빈 면적 자체가 목적은 아니다.
- 크기: 상대적 중요도를 드러낸다.
- 일관성: 화면 사이의 표현과 동작 규칙을 유지한다. 반복되는 장식만으로 충족했다고 하지 않는다.

F형·Z형 읽기 패턴은 참고 패턴이다. 모든 내용과 사용자가 동일한 순서로 읽는다고 강제하지 않는다. 정돈된 간격·위계·타이포그래피·일관성이 실제 과업을 돕는지 판단하고 목적 없는 장식을 줄인다.

### 3.3. 대시보드·찾기·판단 — L01·L17·L19

대시보드는 다음 일곱 기준을 적용한다: 핵심 지표 우선, 관련 데이터 묶음, 통계/차트/목록 카드의 일관성, 차트 과부하 방지, 시간 변화 표현, 필터/검색, 명확한 주요 행동.

자료에 실제로 시간 관측이 있을 때 추세를 표현한다. 보여줄 질문에 맞는 차트를 고르며 종류나 개수를 줄이는 것을 목적으로 하지 않는다. [통계·그래프 선택 기준](statistics-chart-selection.md)의 비교·추세·분포·관계·구성·흐름과 원기록/값 목록/불확실성 계약을 함께 적용한다. 없는 성과·목표·사용자 수·금액을 예시에서 복사하지 않는다.

명확한 탐색과 읽기 쉬운 서비스/도구 구역을 구성한다. 카드 수나 이미지 크기만 바꾼 것을 탐색 개선·전환 효과로 보고하지 않는다.

### 3.4. 공통 시스템과 설계 산출물 — L05·L07·L10·L18·L21·L30

2026-10-02 사용자 후속 결정: 천문대 기준값은 고급 기술 구현과 실제 사용 결과에 따라 조정 가능한 현재 기본값이다. 기존 숫자로 기술 표현을 제한하지 않고 [확정 기준의 기술 적응 원칙](observatory-design-standard.md)에 따라 담당 원본·변경 이유/범위·실제 확인을 함께 갱신한다. 원본 위젯 전체와 바깥 프레임, 정체성·읽기/조작·자료/개인 설정을 보존한다.

색·글자·간격·격자 → 재사용 부품과 속성/상태 → 반복 과업 구역 → 사용 지침/코드 호출을 연결한다. [디자인 시스템](design-system.md)과 [컴포넌트 계약](component-matrix.md)이 현재 토큰과 API의 담당 원본이다.

2026-10-02 사용자 「여기까지, ux, ui, 디자인 기준으로 값을 정해둬라」에 따라 [천문대 UX·UI·디자인 확정 기준](observatory-design-standard.md)과 [역할별 기준값 v2.0.0](observatory-experience-baseline.json)을 채택한다. 어두운 실내·확장 중인 픽셀 하늘/창틀·종이 작업면·네 고정 장소·기능 문구·모션·수리 반응을 현재와 앞으로의 작업에 적용한다. 새 색은 `materials`, 공통 픽셀 값은 `pixelTreatment`가 소유하며 `workSurfaceColors`는 기존 수식 소비자의 v1.1 호환값이다. 기존 중립색/둥근 형태/흐린 그림자가 정체성과 충돌하면 해당 외형과 값을 수정한다. 현재 천문대 원본의 확장·기록 의미·조작 가능성·개인 설정을 보존하고 기준 채택과 코드 소비/화면 검증/배포를 구별한다.

- 와이어프레임은 낮은 구체성의 구조·기능 배치, 주로 단순 색·자리 표시를 다룬다.
- 목업은 높은 구체성의 색·글자·이미지·아이콘·브랜드·시각 위계를 다룬다.
- 프로토타입은 화면 연결과 상호작용을 시험한다. 정적인 목업이나 프로토타입을 실제 저장·서버 제품으로 보고하지 않는다.
- 같은 역할의 부품을 화면마다 새로 만들지 않는다. 필요한 차이는 공통 속성·상태로 표현하고 설계 파일과 실제 토큰/API를 대응시킨다.
- 구조에서 최종 UI로 갈 때 제목·지표·활동·탐색의 목적을 유지한다. 시각적 완성도를 이유로 실제 정보와 기능을 빼지 않는다.
- 설계 사례를 설명할 때 문제·선택 이유·진행 과정·결과를 연결한다. 최종 화면만으로 설계·사용성 확인을 대체하지 않는다.

### 3.5. 간격·격자·자동 배치 — L07·L15·L20

간격을 임의로 늘리지 않고 공통 척도와 토큰으로 관리한다. 큰 구조에는 8 기반 리듬, 작은 조정에는 4 기반 척도를 사용한다. 기존 4px 척도는 8 기반 리듬과 호환되므로 같은 역할의 새 체계를 중복 도입하지 않는다.

원문의 간격 척도와 시작 예시는 모두 유지한다.

| 용도 | 예시 값 |
| --- | --- |
| 기본 8 기반 척도 | 8, 16, 24, 32, 40, 48, 56, 64 |
| 미세 조정 | 4, 8, 12 |
| 구성 요소 | 16, 20, 24 |
| 구역 | 32, 40, 48 |
| 큰 구역 분리 | 64, 80, 96 |
| Figma 변수 예시 | 4, 8, 12, 16, 24, 32, 40, 48, 64 |

패딩·마진·요소 사이 간격·구역 사이 간격을 같은 척도에 연결한다. 내용에 맞춘 자동 배치와 카드/버튼/입력 부품에 적용한다. 후반의 4·12·20 예외를 보존하며 모든 치수를 8의 배수로 반올림하지 않는다. UI 문맥의 pt/px와 인쇄 포인트를 동일한 물리 단위로 오인하지 않는다.

원문의 열 가지 정리인 격자 이해·조화·임의 간격 줄이기·목적별 척도·Figma 설정·반복 적용·위계·안정감·수정 중 정렬·경험 개선을 위 기준으로 실행한다. 직접 확인은 공통 간격, 전체 일관성, 부품 척도, 자동 배치 패딩/간격, 글자 정렬, 아이콘/이미지 간격, 구역 리듬, 기기별 배치의 여덟 범위에서 변경 관련 항목을 고른다.

### 3.6. 타이포그래피와 읽기 — L07·L22·L26·L30

제목·본문·보조 설명의 역할을 분리하고 한글의 읽기·줄바꿈·행간·긴 내용·확대·개인 서체를 확인한다. 색만으로 위계를 해결하지 않는다.

글꼴 구조는 기준선, 대문자 높이, x-height, 내림 기준선, ascender, descender, stem, serif, counter를 통해 비교한다. 개별 예시의 A(apex/crossbar/stem), G(bowl/spur/원문 beard 표기), g(ear/link/loop)와 마무리 여덟 구조(기준선/x-height/ascender/descender/counter/stem/serif/bowl)를 참고한다. 라틴 글자 도식을 한글 구조에 그대로 적용하지 않는다.

글꼴 후보는 Satoshi(현대적·친근한 UI/앱/대시보드), General Sans(균형 잡힌 SaaS/소개/포트폴리오), Cabinet Grotesk(강한 브랜드/대표 제목/에디토리얼)이다. 원문의 대소문자·숫자·문장부호 견본은 모양 비교용이다. 프리미엄이라는 표현을 유료로 해석하지 않는다. 실제 도입 전 한글/필요 기호 지원·라이선스·전송량·현재 환경을 확인한다. 개인 서체를 임의 교체하지 않는다.

### 3.7. 색의 역할·색 모델·팔레트 — L04·L23·L28·L30

바탕·보조·강조의 역할을 먼저 정한다. 60–30–10은 넓은 바탕, 보조 요소, 중요한 행동의 비중을 생각하는 출발점이다. 픽셀 면적의 고정 비율이나 모든 화면의 통과 조건으로 사용하지 않는다. 강조색은 검은색처럼 중립색일 수도 있다.

색상·채도·밝기를 구분하고, 따뜻한 색(빨강/주황/노랑)과 차가운 색(파랑/초록/보라)의 관계를 목적에 맞게 사용한다. 에너지·긴급함·즐거움, 신뢰·차분함·성장·창의성 같은 연상과 음식/상거래/행사, 금융/건강/교육/기술의 예시는 문화와 상황에 따라 달라진다. 특정 색이 감정·신뢰·전환을 보장한다고 주장하지 않는다.

전통적인 RYB 색상환은 빨강/노랑/파랑과 그 혼합인 주황/초록/보라, 여섯 중간색(빨강주황/노랑주황/노랑초록/파랑초록/파랑보라/빨강보라)을 설명하는 예시다. L23의 White 표기는 Yellow와 불일치한다. 화면의 RGB는 빨강·초록·파랑 빛, CMYK는 인쇄의 Cyan/Magenta/Yellow/Black, HSB의 B는 Brightness다. L30의 RGB 설명 반복과 B=Black 표기는 재사용하지 않는다.

### 3.8. 버튼·조작 대상·상태 — L06·L07·L13

버튼은 행동 이름, 충분한 크기, 대비, 안쪽/주변 간격, 상태, 분명한 목적, 주요/보조 위계, 일관성, 접근성, 결과 피드백의 열 기준을 적용한다. 주요 행동을 명확히 하되 필요한 보조 행동·취소·되돌리기를 없애지 않는다.

기본·hover·pressed·focus·disabled·loading·success·error 중 실제 조작에 필요한 상태를 공통 부품으로 연결한다. 추가 중/추가 완료 같은 표시를 실제 처리 상태에 맞추고 성공을 선행 표시하지 않는다. 마우스 상태만 만들고 터치·키보드 상태를 빠뜨리지 않는다.

피츠(거리/크기), 힉(선택 부담), 제이콥(익숙한 관행), 근접성(묶음), 폰 레스토프(구별되는 요소)의 적용 조건을 과업에서 판단한다. 선택지를 줄이는 것이 언제나 좋거나 구별되는 요소가 반드시 먼저 보인다는 절대 규칙으로 쓰지 않는다.

터치 대상은 원문이 권하는 44 CSS px를 기본 설계 후보로 고려한다. WCAG 2.2 AA의 24×24 CSS px 또는 관련 예외와 AAA의 44×44 CSS px를 구별하고, 기존 더 큰 조작 영역을 임의 축소하지 않는다. 실제 레이블·포커스·오류 안내와 조작 간 간격을 함께 확인한다.

### 3.9. 반응형·긴 내용·반복 사용 — L02·L07·L15·L19

데스크톱 화면을 축소한 결과만으로 모바일 대응을 판단하지 않는다. 현재 가용 본문 폭, 긴 한국어, 글자 확대, 터치/키보드, 자료 증가에 맞춰 카드·탐색·입력·표를 조정한다. 잘림·겹침·화면 끝 밀착·과한 버튼 크기·불필요한 가로 이동을 예방한다.

기존 iPhone 17 Pro 세로/가로, iPad Pro 13인치 세로/가로/좁은 창 정책을 따른다. 선택·편집·스크롤/복귀·개인 배치를 화면 변화로 초기화하지 않는다. 빈 자료·결과 없음·로딩·실패·재접속에 필요한 동작을 실제 흐름에 연결한다. [작업 진행 정책](../../docs/작업%20진행과%20검증%20정책.md)의 위험 비례 검사를 따르고 문서 변경에 앱 전체 QA를 강제하지 않는다.

여덟 개를 모두 채택한 참조 범위로 유지하되 한 화면에 억지로 혼합하거나 스타일 선택을 매번 사용자에게 맡기지 않는다. 과업, 내용, 대비, 상태, 기존 제품과의 일관성으로 준이 적합한 조합을 고르고 주요 이유를 남긴다.

## 5. 그림자·빛·장식의 재현 기준 — L08·L09·L24

효과는 층·상태·강조 또는 필요한 시각 자료의 목적이 있을 때 사용한다. 본문보다 강한 장식이나 읽기를 방해하는 빛은 줄인다. 일반 카드의 부드러운 그림자와 네오브루탈리즘의 단단한 그림자를 목적에 맞게 구분한다.

### 5.1. 부드러운 카드 그림자

원문 예시: X=0, Y=6, blur=18, spread=−2, `#000000` 10%. 낮은 불투명도·작은 세로 이동·부드러운 경계로 시작하고 실제 필요에 맞춰 조정한다. 모든 카드의 고정값이나 다른 스타일의 오류 판정으로 사용하지 않는다.

### 5.2. 튜브 조명

- 본체: 600×50px, 반경 25px, 가로 그라디언트 `#00B8FF` → `#FFFFFF` → `#0077FF`, 얇은 흰색 중심 하이라이트.
- 본체 blur=0/opacity=100%; 뒤의 세 복제본은 blur/opacity=20/70%, 60/40%, 120/20%.
- 주변 빛: 아래의 넓은 사각형/타원에 청록→투명 그라디언트, blur=100–200px, opacity=15–25%. 본체·가까운 번짐·넓은 빛의 관계를 조정한다.

### 5.3. 부드러운 원형 덩어리

- 220×220px 원, stroke 없음, `#FFFFFF` → `#FFB4D7` 그라디언트.
- layer blur=300, 조정 범위 250–350.
- glow: X=0/Y=0, blur=160, spread=0, `#FF8CC8` 45%.
- 다섯 원을 겹치고 opacity=100/90/80/85/95% 예시로 깊이를 조정한다.
- 배경: `#6C3B5A` → `#0A0812` 또는 검정, 선택적으로 noise=2–3%.
- 비교 값: blur=250/300/350, glow opacity=35/45/55%.

두 제작 예시의 수치는 재현용이다. 모든 버튼/카드의 기본 효과로 강제하지 않는다. L24의 마지막 유리 관련 표현을 실제 투명 유리 재질로 확인한 것처럼 사용하지 않는다. 정확한 데이터·기하·글자는 효과 또는 AI 이미지로 대신하지 않는다.

## 6. 소개 페이지·재설계·개발 흐름 — L02·L03·L05·L14·L17·L19·L20·L30

### 6.1. 소개 페이지의 설명 순서

대표 영역(가치/이미지/행동) → 신뢰 근거 → 사용자의 문제 → 해결 방식 → 기능 → 이용 과정(3–4단계 예시) → 실제 이용 후기 → 가격 → 자주 묻는 질문 → 마지막 행동의 열 구역을 구조 후보로 사용한다. 실제 목적에 맞춰 순서를 조정한다.

현재 제품에서 제외한 가격/결제 구역을 추가하지 않고, 없는 고객 로고·후기·이용자 수·성과를 만들지 않는다. 신뢰 근거는 실제 저장/보존 동작과 확인한 사실로 제시한다. 제작자의 REDESIGN/BUILD 메시지 유도는 홍보이며 외부 연락의 지침이 아니다.

### 6.2. 재설계 판단

오래되어 보이는 시각 표현, 찾기 어려운 정보/탐색, 모바일에서 무너지는 배치, 방문 후 다음 행동이 불분명한 상태를 실제 화면에서 확인한다. 기존 IT 사이트 비교처럼 제목/대표 영역/탐색/문의 또는 도구 구역/서비스 설명의 위계를 정리한다. 현재 제품에 문의 접수 기능을 다시 도입하지 않는다.

L14의 환자 앱은 여러 화면의 공통 색·구성 요소·폼·목록·차트·이미지를 연결한 참고 사례로 유지한다. 작은 글자로 확인하지 못한 의료 기능·절차·필드·효과를 프로젝트 요구로 만들지 않는다. 이미지의 더 큰 원본 안내를 확인할 후속 항목을 유지한다.

### 6.3. 아이디어에서 사용 가능한 결과까지

문제/사용자/기능/최소 범위 → 사용자 흐름/와이어프레임/UI/프로토타입 → 대상 플랫폼의 프론트엔드/백엔드/DB/API → 기능/사용성/성능/보안/기기 확인 → 허용된 출시 → 실제 반응/분석/개선의 연결을 유지한다. 전체 생애주기를 한 흐름으로 관리하며 문서·UI·코드·서버·배포를 구분한다.

학습 경로 예시는 기초(색/글자/격자) → 디자인 시스템 → 위계/배치/아이콘 → 프로토타입 → 사용자 조사 → 과정과 결과를 설명하는 포트폴리오다. 실제 작업에서는 필요한 기존 지식과 도구를 찾아 적용하며, 모든 학습 단계를 완료해야 작은 수정에 착수할 수 있다는 조건으로 만들지 않는다.

## 8. 기준의 근거·수치·검증

실무 조언, 지각/행동 연구, 공식 접근성 기준, 커뮤니티 기술 명세, 개별 도구, 프로젝트 결정을 구별한다. 유명세·견본 화면·홍보 수치만으로 현재 앱의 성능·학습 효과·접근성 준수를 확정하지 않는다.

기존에 확인한 일차 자료와 전문 설명을 재사용한다. 변한 버전·새 주장·실패가 있을 때 필요한 공식 근거를 추가로 확인한다.

- [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [AA 조작 대상 크기](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum), [AAA 강화 대상 크기](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced): 수치·예외·등급을 구별한다. 자동 검사만으로 전체 준수를 주장하지 않는다.
- [Adobe 색 선택과 모델](https://helpx.adobe.com/photoshop/desktop/adjust-color/choose-colors/choose-colors-with-the-adobe-color-picker.html), [색 모델](https://helpx.adobe.com/creative-cloud/apps/colors/understand-color-modes.html): RGB/CMYK/HSB 오류 정정.
- [NN/g 미니멀리즘](https://www.nngroup.com/articles/characteristics-minimalism/), [플랫](https://www.nngroup.com/articles/flat-design-best-practices/), [브루탈리즘/안티디자인](https://www.nngroup.com/articles/brutalism-antidesign/), [네오브루탈리즘](https://www.nngroup.com/articles/neobrutalism/): 전문 설계 분석이며 해당 외형의 공식 표준이 아니다.
- [Michał Malewicz의 뉴몰피즘 설명](https://hype4.academy/articles/design/neumorphism-in-user-interfaces): 표현 방식과 상태/대비 한계.
- [Material 3](https://m3.material.io/foundations/), [초기 머테리얼 높이/그림자](https://m1.material.io/material-design/elevation-shadows.html): 설계 체계와 표면 관계. 현재 제품 전체 이식 명령이 아니다.
- [Framer 벤투 격자](https://www.framer.com/dictionary/bento-grids), [Pentagram 에디토리얼 설명](https://www.pentagram.com/editorial-design), [실제 잡지 사례](https://www.pentagram.com/work/the-new-republic): 도구/제작자의 개념 설명과 선행 사례.

실제 변경에서는 관련 원칙을 토큰·부품·흐름에 적용하고 기존 Storybook/직접 브라우저/회귀 도구로 필요한 읽기·조작·저장·복귀를 확인한다. 앱 변경의 필수 빌드/기기/CI는 기존 정책을 따른다. 지침 링크 확인, 코드 검사, 실제 화면, 서버 적용, 공개 배포, 물리 기기, 장기 사용·학습 효과는 각각 확인한 범위로 보고한다.
