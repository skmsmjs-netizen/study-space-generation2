# ManSeekSong OS 레이아웃 확정 기준

**버전1.0.0 · 2026-10-02 채택.** 사용자 「OS 정체성에 방금 최종 레이아웃 파일을 바탕으로 기준을 설정」「현재뿐 아니라 앞으로 배치할 요소」「Figma에 기준」「웹앱은 반드시 파일의 레이아웃 중 하나」 결정을 적용한다. 현재·앞으로의 OS 설계/구현/수정/리뷰/Figma/유지보수에서 이 문서와 [선택 계약](layout-standard-contract.json)을 따른다.

**웹앱의 화면과 과업 구역은 채택한 [통합 레이아웃 파일](layout-catalog/uiux_layout_figma_guide.expanded.txt)에 등록된 패턴에서 선택한다.** 원문0–186과 추가187–198의 안정 ID `L000–L198`를 유지한다. 도입, 그리드, 도구 기능, 크기 속성, 실패 조언은 화면 패턴과 구별한다. 어느 화면이나 8pt·Fixed·Frame만 선택하고 레이아웃 결정을 완료했다고 처리하지 않는다.

최신 사용자 정정이 우선이며 나머지 기준은 충돌하지 않는 범위에서 유지한다. 장식 비율·예시 숫자를 읽기/조작·실제 과업·보존보다 우선하지 않는다. 원문/ID/저장 키/초안/이력/개인 배치·테마·서체·서버 권한은 유지한다. 새 기준 때문에 개인 Canvas를 자동 재배치하거나 기능을 삭제하지 않는다.

Figma 공식 구조/Auto Layout, CSS Grid/박스/단위 명세, Carbon의 간격 방법, WCAG/APG의 관련 조건은 [전 단계 검토](layout-catalog/expansion.md)의 확인 범위와 한계를 재사용한다. Figma 공식 기능·CSS 초안·특정 디자인 시스템·연구 관찰·프로젝트 규칙을 구별한다. 새로 정한 것은 OS의 패턴 선택 계약과 공간/과업/요소별 조합이며 보편 최적 UI나 학습 효과 법칙이 아니다.

## 2. 등록된 패턴을 선택하는 규칙

1. 실제 과업을 읽기·입력·찾기·비교·조절/실행·관계 탐색·계획·변경/복구 중에서 정의한다.
2. 화면의 대표 패턴 `primaryPattern`을 등록 목록에서 고른다. 내부의 목록/상세/표/보조면은 `secondaryPatterns`와 독립 구역으로 연결한다.
3. 넓은/좁은 화면에서 사용하는 등록된 대체 구조와 의미 순서를 정한다. 폭만 줄인 축소판으로 대체하지 않는다.
4. 그리드·흐름·Hug/Fill/Fixed·토큰은 별도 축으로 연결한다. 대표 패턴을 대신하지 않는다.
5. 빈 상태/오류/읽기 전용/선택/처리 중은 같은 과업의 상태이다. 실제 내용과 복구 행동을 연결한다.
6. 선택 이유·소스·원문/초안/개인 상태 보존·확인 근거를 남긴다. 새 패턴이 필요하면 기존 변형/조합으로 해결되는지 먼저 확인하고, 해결되지 않는 요구만 사전에 등록한 뒤 사용한다.

**한 화면의 대표 패턴은 하나이며 내부에서 다른 등록 패턴을 조합할 수 있다.** 공통 외곽을 대표 과업 패턴과 혼동하지 않는다. `L170 Modal`은 보조면의 외곽 패턴, `L053 Form`은 내부 과업 패턴처럼 함께 기록한다. `L064–L070`은 탐색/보조면에서, `L160–L170`은 해당 부품/보조면의 레시피로 쓸 수 있지만 앱 전체의 대표 구조를 대신하지 않는다.

현재41경로·29모달·41보조면의 개별 지정은 [전체 대응표](layout-standard/entity-layouts.md)와 계약의 `entityLayouts`를 따른다. 이 지정은 앞으로 적용할 정식 목표이며 과거 소스가 전부 준수한다는 판정이 아니다. 별칭 경로는 새 화면을 만들지 않고 기존 실제 목적지의 기준을 따른다.

## 5. 폭·높이·간격·조판

**값은 담당 원본의 현재 기본값이며 내용과 기술 구현에 따라 보정한다.** 아래 수치는 root16px에서의 표시를 함께 적는다. 개인 글자 크기가 달라지면 rem이 변하며 이를 강제로 px로 고정하지 않는다. Figma 숫자는 기준 글자 크기에서의 설계 투영이다.

| 역할 | 현재 참조/값 | 적용 조건 |
| --- | --- | --- |
| 일반 글자 기초 | metrics.type.body 1rem/1.65/400 | 부품·역할별 스타일의 기초이며 종이 본문은 아래 별도 값 적용 |
| 종이 본문 | metrics.paper.bodyTypography: 굵기500/행간2/자간−0.05em, 읽기 면40rem 이하1.85/−0.025em | 양쪽 정렬/마지막 줄 시작 정렬. 개인 서체·폭·명시 줄바꿈 보존; 제목·조작·수식·코드는 역할 스타일 유지 |
| 제목/구역/라벨/캡션 | type.title1.75rem(좁은1.5), heading1.25, label0.9375, caption0.875 | 역할별 사용; 제목/라벨 줄바꿈 성장 |
| 읽기 최대 폭 | layout.readingMaxRem48 →768px | 최대값; 좁은 컨테이너에 최소 폭으로 강제하지 않음 |
| 짧은 변경/대화면 최대 폭 | layout.dialogMaxRem36 →576px | 긴 편집은 주면/상세; 가상 키보드·지역 스크롤 |
| compact/wide | layout.compactContainerRem40 / wideContainerRem64 | 콘텐츠 역할별 후보; 본질적2D·개인 폭 예외 |
| 페이지/종이 여백 | 1.5rem, 좁은1rem | 창틀 바깥 공간과 구별; root16에서24/16px |
| 구역/필드/관련 간격 | 1.5rem /1rem /0.5rem | 관계에 따른 역할; 모든 간격을 같은 배수로 강제하지 않음 |
| 기본 간격 scale | 0/4/8/12/16/24/32/48/64, 별도group18 | 실제 token 소비; 이름8pt를 CSS pt로 치환하지 않음 |
| 조작 높이/아이콘 목표 | control.heightPx48 / iconTargetMinPx44 | 최소값; 긴 글·확대에 높이 성장 |
| 초점/간격 | focusPx2 / focusOffsetPx3 | 틀·고정 바·부모 clip에 가리지 않음 |
| 창틀 | window.framePx8 / compactFramePx4 | 위젯 바깥; 전체 원본 비율/장면 extent 유지 |
| 종이/글자 | opacity1 /rotation0 /본문 밑 texture0 | 작업 글은 차분하고 정지한 읽기 면 |
| 본문 정렬 | paper.bodyAlignment justify /lastLine start | 제목/버튼/표/수식/코드/공간 라벨은 의미 정렬 |

축별 크기 결정은 다음을 따른다. 짧은 이름/명령은 가로 Hug와 필요 시 줄바꿈, 주면/입력은 가로 Fill+min/max, 본문/답/오류는 세로 내용 성장이다. 아이콘/장면 비율은 해당 고정/비례 축을 유지한다. 입력·답·오류를 고정 높이로 자르지 않는다. Max Height는 끝까지 읽기/키보드 접근·스크롤 주체를 함께 정했을 때만 사용한다.

현재 앱의 catalogue 카드18rem, 외곽 탐색15/12/11rem, 일부64rem/40rem 전환은 실제 소비 중인 조건으로 확인했다. 이는 기존 소스의 관측값이며 모든 화면의 최적값으로 새로 승격하지 않는다. 기존 토큰으로 표현할 수 없는 새 역할 값은 담당 baseline에 이유/범위/확인 결과를 추가한 뒤 Figma와 소비 코드를 함께 연결한다. 이 기준 작업은 값을 화면별로 복제하지 않는다.

본문의 양쪽 정렬을 유지하면서 좁은 한글/긴 영어/개인 서체의 간격을 확인한다. 사용자 스타일/읽기 조정에 맞춘 내용 성장을 막지 않는다. WCAG AAA의 양쪽 정렬 해제 조건과 AA의 간격 변경 내성을 구별하고, 기본값만으로 전체 적합성을 주장하지 않는다.

## 6. 반응형·스크롤·누적

가용 컨테이너 폭이 판단 기준이며 장치 이름만으로 고정하지 않는다. 기존40rem 미만 한 읽기 열 정책을 유지하되, 패널 최소 폭/조작/글자 확대가 먼저 깨지면 해당 구역을 더 일찍 전환한다. 기본 전환 후보는 `주면에 필요한 폭 + 보조면에 필요한 폭 + 구역 간격 + 안쪽 여백`이며 실제 내용/조작으로 보정한다.

| 대상 | 전환/증가 규칙 |
| --- | --- |
| 탐색 | 넓은Sidebar/TopNav→등록 Drawer/BottomNav. 중요 기능 접근·현재 위치 유지 |
| 목록/상세 | 동시에 표시→목록/상세 순차 진입. 뒤로 가면 선택/검색/스크롤 복귀 |
| 분할 편집/연산 | 나란히→주면+보조면/순차. 같은 입력·원문·조건 유지 |
| 카드/자료 | 가용 폭과 카드 내용으로 열 수 결정; 높이는 내용 성장. 원문 전체는 요약 카드 밖 상세 제공 |
| 글/답/오류 | 의미 순서대로 줄바꿈/성장; 숨기거나 말줄임만으로 필수 정보 제거 금지 |
| 표/수식/Canvas | 의미상2D 부분 안에서 pan/zoom/가로 탐색·값/항목 접근. 주변 설명/조작은 재배치 |
| 목록 누적 | 필요한 필터/접기/분할 로딩/가상화 선정; 실제 규모·선택/ID/접근성 유지 |
| 결과/갱신 | 관련 영역 갱신; 입력/초점/수동 폭/시점을 반복 초기화하지 않음 |

일반 읽기 면의320 CSS px 상당 폭과 글자 확대, 해당 간격 조정 조건을 확인한다. 본질적2D 예외는 영역에만 적용하며 전체 앱을 예외로 묶지 않는다. 문서/목업 검사와 실제 브라우저/한글 입력/물리 기기/장기 사용을 구별한다.

스크롤은 기본 문서 흐름을 우선하고, 독립 작업이 필요한 패널/2D/결과에만 지역 스크롤을 둔다. scroll 체인이 과업을 막지 않아야 한다. 고정 바와 가상 키보드가 초점·입력·닫기·실행을 가리지 않게 한다. 가로 보드·긴 표에는 드래그만 강제하지 않고 명시적 이동/선택 대안을 둔다.

## 7. 앞으로 추가할 요소의 배치 계약

현재 구현되지 않은 요소도 역할을 먼저 지정하고 계약의 `futureElementClasses`에서 등록 패턴·크기/증가·전환·보존 조건을 고른다. 24개 요소 분류는 [미래 요소 표](layout-catalog/expansion.md)의 위젯/탐색/제목/행동/상태/계층/찾기/본문/수식·코드/PDF·필기/질문/조절/그래프/관계/보드/일정/속성/오류/처리/복구/API·로그/시간 자료/조건부 협업/운영을 전부 다룬다.

새 GPU/3D/셰이더/수리 엔진은 기능을 Figma 목업에 맞춰 없애지 않는다. Figma에는 전체 범위의 가벼운 대표 표현·native 조작·실제 구현 참조를 두고 실제 앱에 계산/편집/조작/값/오류를 연결한다. 기술 표현의 상한은 두지 않으며 관련 최소 가독성·대체 접근·실패/복귀는 유지한다.

협업/공유/결제/지원 같은 조건부 분류는 새 기능 채택이 아니다. 실제 연결/운영과 별도 권한·기존 제외 결정이 충족된 경우에만 배치에 적용한다. 없는 동료·가격·문의 회신·승인·저장 결과를 만들지 않는다.

새 요소는 다음을 모두 기록해야 한다.

```text
실제 기능/구역 ID · 상위 화면/역할 · 사용자가 끝낼 과업
등록 primaryPattern · secondaryPatterns · 외곽/본문/보조면의 범위
장소/재료 · 실제 정보/내용/단위/상태의 의미 순서
width/height 반응 · 토큰 참조 · 긴 내용/누적 대응
좁은 화면 전환 조건/등록 대체 구조 · 스크롤/키보드
진입→입력/조작→결과→취소/닫기/복귀 · 실패/재시도
원문/ID/초안/이력/개인 설정/배치/권한 보존
실제 구현/Figma 참조 · 확인 환경/결과 · 미확인
```

## 8. 복귀·실패·장기 사용

공통 도구·모달·상세를 닫으면 진입 전 실제 대상/방향/포커스/편집기와 필요한 시점으로 돌아간다. 없어진 대상이면 관련 목록과 이유를 제공한다. 단순 화면 전환으로 새 편집기를 만들거나 원문/초안을 초기화하지 않는다. 저장 완료는 실제 저장 결과로만 표시한다.

모달은 배경 조작 제한과 초점 진입/내부 이동/닫기/복귀를 연결한다. 비모달 곁면은 주면과 오갈 수 있어야 한다. 패널 폭/위치/선택/펼침의 수동 값은 해당 과업의 보존 기간을 정하고 초기화·되돌리기·자동 기본값 복귀를 제공한다. 새 자료가 들어왔다는 이유로 사용자의 상태를 덮어쓰지 않는다.

빈 상태·미기록·미정 날짜·부분 수행·불확실을 실패/0/숙달로 자동 해석하지 않는다. 지식의 닫힌 네모·실제 순서·관계 표시와 원문/조건/예외/이력을 연결하고 네모를 기억 효과의 증거로 삼지 않는다.

## 9. Figma 운영과 적용 판정

현재·앞으로의 실제 Figma 설계에는 [재사용 템플릿 페이지](https://www.figma.com/design/YHmD1PpWWfR9JGTEs77JsX?node-id=250-180)의 등록 패턴 Component Set과 Width=wide/narrow 변형을 우선 재사용한다. 실제 원본 ID는 [패턴 연결](layout-standard/implementation/pattern-map.json), 현재111개 기능의 기존 도면/새 보조면 연결은 [현재 대응](layout-standard/implementation/current-coverage.json)이 담당한다. 인스턴스의 과업 제목/본문과 실제 부품을 연결하고 긴 내용/조건/실패/복귀를 확인한다. 템플릿 작성·기존 프레임 적용·전체 최종 검증·실제 앱 소비를 각각 구별하며, 현재 적용 결과와 도구 한도로 남은 범위는 [구현 기록](layout-standard/implementation/README.md)에 유지한다.

레이아웃 전용 페이지에서 공통 외곽,10프로필의 넓은/좁은 형태, 전체111대응, 미래24요소, 값 참조, 등록 항목 색인, 상태/복귀, 선택/변경 절차를 읽을 수 있게 한다. 설명·제목·구역은 편집 가능하며 Auto Layout으로 내용이 늘어날 수 있어야 한다. 전체 앱 화면 스크린샷을 기준 페이지의 편집 가능한 UI 대신 넣지 않는다. 복잡한 원본 장면은 사용자 채택 목업 정책대로 전체 범위 이미지를 재사용한다.

기존 페이지/원본/인스턴스/오버라이드/이동·ID를 유지한다. 새 페이지의 근거와 생성/재조회 노드 ID를 [실제 결과](layout-standard/README.md)에 남긴다. 공통 재료/간격 변수·Noto Sans KR 역할 스타일을 재사용하며 기준 문서의 예시 폭을 새로운 제품 토큰으로 만들지 않는다.

**선택 계약 검사는 문서 범위/참조를 검증하고 실제 UI 준수는 소스와 화면으로 판정한다.** 새 화면/요소를 추가하거나 관련 화면을 크게 수정하면 대응 계약을 갱신하고 변경에 필요한 정상·긴 내용/좁은 화면·실패/복귀 조건을 확인한다. 작은 변경에 전체111실행·전체 기기 QA를 강제하지 않는다. 구현 전환 시 핵심 진입/조작/저장/복귀까지 연결한다.

### 확인 명령

```sh
python3 generation2/docs/layout-standard/scripts/build_standard.py
```
