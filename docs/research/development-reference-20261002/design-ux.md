# ManSeekSong OS — 디자인·UI·UX·Figma 대표 기준 조사

확인일: 2026-10-02. 사용자 요청 「본 개발에 있어서 표준 삼을 대표적인 사이트, 기준, 표준, 라이브러리, 고급 스킬, 고급기술 등을 다 조사해」 중 C01 사용자 연구/문제 정의, C02 정보 구조·흐름·콘텐츠, C03 디자인 시스템, C04 한글·색, C05 접근성, C06 Figma를 담당한다. 대표 자료 28개(D01–D28)와 설치된 Figma 스킬 5개의 관련 본문을 실제 열어 확인했다. 세계의 모든 자료를 전수 조사했다는 뜻은 아니다. 원본/초록/공개 소개/검색 본문만 확인한 경계를 항목마다 남긴다.

## 선택 결론

**천문대 정체성을 중심으로 자체 디자인 시스템을 만들되, 과업·조작·접근성·표현·도구의 기준은 각각 알맞은 기존 자료를 조합한다.** 현재 정체성은 살아 움직이는 픽셀 세계와 그 안의 정확한 공부 작업면이다. 외형은 [천문대 정체성](../../observatory-identity-20261001.md)과 [기준값 JSON](../../observatory-experience-baseline.json), 공통 동작은 [최우선 디자인·UI·UX](../../design-ui-ux-priority.md)와 기존 저장/복귀 계약을 출발점으로 삼는다. 본 연구의 권고가 해당 지침이나 실제 앱을 자동 수정하지 않는다.

- **기본 작업 기준:** ISO 공개 개요의 인간중심설계 범위, Double Diamond의 작은 문제 발견/시험, NN/g의 상태·통제·복구 점검, GOV.UK의 경험 지도, WCAG 2.2/APG를 목적별로 사용한다. 대표 기준은 서로 대체재가 아니다.
- **디자인 시스템의 구조:** 현재 토큰과 부품을 유지하고 천문대의 값·윤곽·빛·상태를 연결한다. DTCG는 교환 형식, Carbon/Spectrum은 운영 사례, Material/Apple은 선택적 참고다. 네 회사의 외형을 한 화면에 섞거나 모두 설치하지 않는다.
- **Figma의 역할:** 현재 화면과 목표 화면을 구별하고, 실제 코드와 연결된 변수·부품·상태·흐름을 편집 가능한 구조로 관리한다. Storybook의 실제 부품 상태와 비교한다. Code Connect는 요금제/권한이 맞을 때 채택할 도구이며 전체 앱 개발의 선행조건은 아니다.
- **고급 표현의 위치:** 천문대의 살아 있는 세계는 실제 렌더러·입력 반응·성능/대체 경로로 발전시킨다. Figma에는 대표 상태와 상호작용 계약을 남기고, GPU/시간 기반 동작의 실제 결과는 앱에서 확인한다.
- **최종 선택 기준:** 해결하는 실제 과업, 천문대 정체성과의 일치, 읽기/조작 가능성, 현재 코드/토큰과의 호환, 자료 누적/복귀/실패 대응, 권한·비용·유지보수를 함께 판단한다. 스킬/패키지 개수와 고급 효과의 수는 품질 지표로 사용하지 않는다.

| C01 사용자 연구·문제 정의 | D04·D06·D07 | 실제 공부 후 여러 주제를 기록하고 중단 후 돌아오는 상황을 관찰 | 끝낸 과업, 막힌 지점, 불필요 입력, 관찰과 가설 구별 |

## 기준·방법·제품·참고 자료의 지위

아래의 `기본 권고`는 이번 연구의 선정 결과이며 새 프로젝트 규칙의 자동 채택을 뜻하지 않는다. `기존 유지`는 현재 프로젝트 지침에 이미 연결된 경로를 가리키며 제품 전체 통과라는 뜻은 아니다. `조건부`는 실제 필요·호환·권한 확인 뒤 선택한다. `참고`는 구조/사례/영감의 출처다.

### D01 — WCAG 2.2

- 지위/선정: **W3C Recommendation · 기존 유지**
- 목적·천문대 적용: 웹 접근성의 시험 가능한 성공 기준과 A/AA/AAA 등급을 제공한다. 천문대에서도 읽기·키보드·초점·색 의미·모션·오류 복구를 판단하는 기준으로 유지한다.
- 확인 범위와 한계: 일부 대비나 자동검사 통과를 전체 적합성으로 확대하지 않는다. 픽셀 미감 자체를 정하지 않는다.
- 출처: [WCAG 2.2](https://www.w3.org/TR/WCAG22/) · 확인 2026-10-02

### D02 — WAI-ARIA Authoring Practices Guide

- 지위/선정: **공식 비규범적 구현 지침 · 기본 권고**
- 목적·천문대 적용: 탭·대화상자·콤보박스 등 위젯의 역할·상태·키보드 조작 패턴을 제공한다. 픽셀 외형 아래의 익숙한 조작을 설계하는 데 적합하다.
- 확인 범위와 한계: APG 예제는 제품 완성품이나 WCAG 인증이 아니다. 네이티브 HTML을 먼저 검토하고 실제 브라우저/입력으로 확인한다.
- 출처: [WAI-ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/) · 확인 2026-10-02

### D03 — Design Tokens Format Module 2025.10

- 지위/선정: **안정된 커뮤니티 기술 명세 · 기본 권고**
- 목적·천문대 적용: 도구 사이에서 토큰 값·유형·참조를 교환하는 형식을 정의한다. 기존 CSS/JSON 원본과 Figma 변수 사이의 변환 경계를 정하는 데 사용한다.
- 확인 범위와 한계: DTCG가 안정된 구현용 명세로 발표했지만 W3C Standard도 W3C Standards Track도 아니다. 형식 채택이 자동 동기화를 만들지는 않는다.
- 출처: [Design Tokens Format Module 2025.10](https://www.designtokens.org/tr/2025.10/format/) · 확인 2026-10-02

### D04 — ISO 9241-210:2019

- 지위/선정: **인간중심설계 국제표준 공개 개요 · 기본 권고**
- 목적·천문대 적용: 공식 공개 개요는 상호작용 시스템 생애주기의 인간중심설계 원칙과 활동을 다룬다. 2025 재확인된 현행판임을 확인했다.
- 확인 범위와 한계: 유료 본문을 읽거나 적합성을 감사하지 않았다. 공개 개요 자체도 개별 기법 전체나 모든 프로젝트 관리를 제공하지 않는다고 설명한다.
- 출처: [ISO 9241-210:2019](https://www.iso.org/standard/77520.html) · 확인 2026-10-02

### D05 — ISO 9241-110:2020

- 지위/선정: **상호작용 원칙 국제표준 공개 개요 · 기본 권고**
- 목적·천문대 적용: 일반적인 사용자-시스템 상호작용 원칙을 적용하는 틀을 제공한다. 2025 재확인된 현행판임을 확인했다.
- 확인 범위와 한계: 유료 본문 미열람. 공식 개요가 미감·마케팅·기업 정체성을 다루지 않는다고 명시하므로 천문대 미감의 정답으로 사용하지 않는다.
- 출처: [ISO 9241-110:2020](https://www.iso.org/standard/75258.html) · 확인 2026-10-02

### D06 — Design Council Double Diamond

- 지위/선정: **설계 방법 프레임워크 · 기본 권고**
- 목적·천문대 적용: 발견·정의·개발·전달을 통해 문제의 이해와 대안 탐색/작은 시험을 연결한다. 현재 앱에서 실패·혼란이 있는 과업을 좁혀 개선하는 방법으로 쓴다.
- 확인 범위와 한계: 국제표준이나 품질 보증이 아니다. 기존 조사와 합의가 있는데 매번 전체 프로젝트를 처음부터 조사하는 절차로 만들지 않는다.
- 출처: [Design Council Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/) · 확인 2026-10-02

### D07 — Nielsen Norman Group 10 Usability Heuristics

- 지위/선정: **전문가 사용성 휴리스틱 · 기본 권고**
- 목적·천문대 적용: 상태의 가시성·사용자 통제·일관성·오류 방지/복구 등을 점검한다. 저장 대기/실패, 돌아가기, 익숙한 한국어 행동명을 평가한다.
- 확인 범위와 한계: 원문 스스로 구체 규격이 아닌 넓은 경험칙이라고 설명한다. 실제 사용자 관찰을 대체하지 않고 법칙별 효과를 앱의 학습 효과로 옮기지 않는다.
- 출처: [Nielsen Norman Group 10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) · 확인 2026-10-02

### D08 — GOV.UK Creating an experience map

- 지위/선정: **정부 서비스 설계 실무 지침 · 기본 권고**
- 목적·천문대 적용: 시간에 따른 사용자 행동과 서비스 접점을 정리한다. 진입→공부→기록→중단→복귀와 화면 뒤 저장을 연결할 때 사용한다.
- 확인 범위와 한계: 공공 서비스 맥락의 방법이므로 현재 개인 공부 도구에 필요한 수준으로 축소한다. 실제로 관찰하지 않은 감정과 행동을 사실로 채우지 않는다.
- 출처: [GOV.UK Creating an experience map](https://www.gov.uk/service-manual/user-research/creating-an-experience-map) · 확인 2026-10-02

### D09 — Material Design 3 Foundations

- 지위/선정: **기업 공식 디자인 시스템 · 참고**
- 목적·천문대 적용: 공식 색인에서 토큰·상태·배치·접근성·브랜드 맞춤 기초를 확인했다. 공통 부품의 상태와 역할을 빠뜨리지 않는 참고가 된다.
- 확인 범위와 한계: 동적 상세 페이지의 전 본문은 읽지 않았다. M3의 외형·둥근 모서리·플랫폼 관행을 픽셀 정체성보다 우선하거나 관련 라이브러리를 자동 도입하지 않는다.
- 출처: [Material Design 3 Foundations](https://m3.material.io/foundations/) · 확인 2026-10-02

### D10 — Apple Human Interface Guidelines — Motion

- 지위/선정: **플랫폼 공식 디자인 지침 · 참고**
- 목적·천문대 적용: 공식 검색 본문에서 모션의 상태 전달·피드백 역할과 입력/접근성 설정에 따른 조정을 확인했다. 천문대의 세계 표현과 즉각적인 조작 반응을 나누는 데 참고한다.
- 확인 범위와 한계: 일반 HIG 페이지는 동적 본문 추출이 제한됐다. Apple 플랫폼 고유 외형이나 Liquid Glass가 웹앱의 목표 미감이 되는 것은 아니다.
- 출처: [Apple Human Interface Guidelines — Motion](https://developer.apple.com/design/human-interface-guidelines/motion) · 확인 2026-10-02

### D11 — IBM Carbon Themes

- 지위/선정: **기업 공식 디자인 시스템 · 참고**
- 목적·천문대 적용: 테마에 따라 값이 바뀌어도 역할과 사용 의미를 유지하는 운영 방식을 참고한다. 따뜻한 종이/밤 작업면의 같은 버튼과 입력 상태를 연결한다.
- 확인 범위와 한계: Carbon 전체 외형·밀도·패키지를 가져오는 권고가 아니다. 천문대 원본과 기존 사용자 설정의 역할을 유지한다.
- 출처: [IBM Carbon Themes](https://www.carbondesignsystem.com/building-blocks/foundations/themes/overview) · 확인 2026-10-02

### D12 — Adobe Spectrum Design Data — Tokens

- 지위/선정: **기업 공식 디자인 데이터/운영 사례 · 참고**
- 목적·천문대 적용: 색 팔레트·의미 별칭·컴포넌트별 색·조판·레이아웃 데이터가 분리된 공식 목록을 확인했다. 역할→부품→상태로 토큰을 조직하는 비교 기준이다.
- 확인 범위와 한계: Spectrum 외형 복제나 전체 React Spectrum 설치 권고가 아니다. 이전 Spectrum 페이지 일부는 오류가 있어 현재 공식 데이터 문서를 함께 확인했다.
- 출처: [Adobe Spectrum Design Data — Tokens](https://opensource.adobe.com/spectrum-design-data/tokens/) · 확인 2026-10-02

### D13 — Figma variables, collections and modes

- 지위/선정: **제품 공식 기능 문서 · 기본 권고**
- 목적·천문대 적용: 변수·별칭·모드로 공통 값과 밝음/어두움 같은 문맥을 관리한다. 천문대 토큰을 개별 화면마다 다시 입력하지 않는 설계 기반이다.
- 확인 범위와 한계: 모드 수는 요금제에 의존한다. 로컬 앱 JSON과 자동 양방향 동기화된다는 뜻이 아니며 연결 코드를 별도로 검증해야 한다.

## 법칙을 실제 설계 판단으로 사용하는 범위

Fitts(D26)는 작은 도형 자체보다 **누를 수 있는 목표의 크기·거리·정확도**를 보게 한다. 픽셀 아이콘을 작고 정밀하게 유지하면서 조작 영역을 확보할 수 있다. 서로 가까운 위험 행동이나 화면을 가리는 거대한 버튼까지 정당화하지 않는다.

Hick(D27)은 사용자가 당장 구별해야 하는 낯선 선택을 줄이거나 분류할 근거 후보다. 자주 쓰는 기능을 숨겨 더 많이 탐색하게 하면 실제 비용이 늘 수 있으므로, 선택지 수만 세지 않고 **과업을 선택하고 끝내는 시간·되돌아감·오류**를 관찰한다.

게슈탈트의 근접성·유사성·공통 영역은 **어떤 요소가 한 덩어리로 읽히는지**를 판단하는 도구다. D28의 원 연구 초록은 공통 영역이 다른 묶임 단서와 상호작용함을 보여준다. 원문이 다른 기록들을 장식 때문에 같은 의미로 묶지 않으며, 같은 저장 범위의 입력과 버튼은 관계가 드러나게 놓는다. 이러한 적용은 이 프로젝트에 대한 설계 판단이고 학습 효과의 검증은 아니다.

Laws of UX(D21)는 개념을 찾는 색인으로 두고, 중요한 효과·수치·제한은 원 연구나 전문 근거로 올라가 확인한다. 7±2를 메뉴 개수, 한 연구의 반응 시간을 모든 UI의 허용 지연, 미감을 실제 사용성과 동일하게 환산하지 않는다.

**스킬 간 충돌도 확인했다.** `figma-use`는 여러 페이지 작업을 병렬 호출하라고 설명하지만, `figma-generate-library`는 라이브러리 변경 호출을 순차로 하라고 명시한다. 라이브러리를 만들 때는 더 구체적인 도메인 스킬의 순차 변경 규칙으로 실행하고, 독립 자료 조사만 병렬화하는 것이 적합하다. 스킬의 도구 호출 방식은 실행 시점의 상위 지침과 실제 도구 제약을 다시 따른다.

`figma-code-connect`에는 코드 부품 대응을 사용자에게 확인하라는 단계가 있다. 실제 실행에서는 이미 사용자가 채택한 대응이나 명확한 코드 원본으로 해소되는 결정을 불필요하게 다시 승인받지 않는 상위 지침을 먼저 적용한다. 외부 라이브러리 발행·권한 변경·구독 결제는 각각의 기존 허용 범위를 확인한다. 이번 연구에는 그러한 행동이 없다.

Figma 변수/변형의 기본 사용 가능성과 팀 라이브러리 발행, Code Connect, MCP 읽기 한도는 각각 다른 조건이다. D13–D17을 혼합해 “유료여야 Figma 설계를 시작할 수 있다”거나 “읽기 제한 때문에 로컬 연구도 불가능하다”고 판단하지 않는다. 실제 계정·파일·seat를 조회하지 않았으므로 현재 사용자의 연결 가능 여부를 확정하지 않는다.

## 현재 프로젝트에 권하는 적용 순서

1. **현재 구현을 식별한다.** 관련 Git 버전과 실제 화면에서 화면/과업/공통 부품/상태/입력·저장·복귀 목록을 만든다. 기존 천문대의 확장 중인 실제 renderer를 표현 원본으로 표시한다.
2. **불편과 목표를 짝지어 좁힌다.** 예: “홈에서 하던 자료를 다시 찾는다”, “공부 뒤 여러 주제를 기록하고 다시 연다”. 정체성 문구와 실제 행동을 함께 평가한다.
3. **공통 값과 상태를 Figma에 연결한다.** 현재 토큰과 새 천문대 기본값의 적용 상태를 구별하고, 실제 사용자 설정·의미색·저장 상태를 보존한다. 새 장식색을 별도 CSS에 복제하지 않는다.
4. **한 완결 과업을 설계·구현한다.** 정상/빈 자료/긴 한글/대기/실패·재시도/중단·복귀 중 관련 조건을 같은 흐름에 넣는다. 저장 계약은 이 단계에서 프론트엔드와 함께 정하고, 기존 백엔드를 다시 만드는 범위로 확대하지 않는다.
5. **실제로 비교한다.** Figma는 구조와 목표, Storybook은 부품 상태, 앱은 조작·저장·복귀를 확인한다. 필요한 현재 기기 모사와 실제 기기 증거를 구분한다.
6. **검증된 규칙을 다음 과업으로 확장한다.** 버전·예외·남은 조건을 같은 대응표에 남긴다. 이미 통과한 변경을 새로운 이유 없이 전체 재검사하지 않는다.

## 품질을 관찰하는 방법

현재 앱의 반복 사용과 자료 누적에 맞게 **과업 성공, 잘못 누른 조작, 되찾기, 중단 후 복귀, 원문/초안 보존, 입력 지연**을 관찰한다. 적은 예시뿐 아니라 관련 긴 글·늘어난 목록·좁은 화면·저장 실패를 확인한다. 유효한 규모와 목표값은 현재 자료·관찰에서 정하며 이번 연구가 임의의 표본 수나 장기 성능 목표를 확정하지 않는다.

“천문대 같은 느낌”, “머물고 싶음”, “집중하기 좋음”은 디자인 의도와 실제 사용자의 반응을 구분한다. 과업 후 표현을 먼저 묻고 그 이유를 관찰할 수 있지만, 취향 반응을 학습 효과나 숙달로 환산하지 않는다. 화려한 표현과 빠른 입력을 함께 달성하는지가 이 제품에서 확인할 구체적인 질문이다.
