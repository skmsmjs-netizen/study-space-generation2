# 첨부 파일을 포함한 탈퇴와 재개

2026-10-03 사용자 일곱 항목 마감 요청으로 기존 개인 계정의 탈퇴에 Storage 정리와 재개를 연결했다. 이 기능을 구현·배포한 작업에서 실제 개인 계정을 삭제하지 않는다. 시험은 새로 만든 합성 계정과 첨부 파일만 사용한다.

탈퇴는 본인 인증과 `탈퇴` 확인을 거친다. `study_begin_withdrawal`이 마지막 관리자를 먼저 보호하고 진행 상태를 저장한다. 진행 중에는 계정의 승인 상태를 중지하며, 관리자 재승인이 끼어들어도 공부 저장·읽기와 Storage 업로드가 다시 열리지 않는다. 기존 쓰기와 Storage 삽입은 계정 권한 행을 잠가 탈퇴 시작과 순서를 맞춘다.

한 요청은 최대50개 파일을 실제 Storage API로 삭제한다. 소유 계정이 일치하는 객체와 해당 계정 경로의 소유자 없는 기존 자료만 대상으로 삼는다. 다른 소유자가 지정된 파일은 경로가 비슷해도 정리하지 않는다. DB에서 Storage 메타데이터만 지워 파일을 남기는 방법은 사용하지 않는다. 일부 삭제 후 실패하거나 요청이 끊기면 계정과 브라우저 기록을 유지하고, 다음 요청이 실제 남은 파일부터 이어간다. 마지막 요청은 파일 잔존을 다시 확인한 뒤 Auth와 관련 서버 기록을 원자적으로 삭제한다.

브라우저는 요청 전에 임의 UUID 확인 번호를 보관한다. 계정 삭제와 동시에 완료 확인을 기록하며, 그 확인에는 계정 식별자와 공부 내용이 없다. 최종 응답이 유실되어 로그인도 사라진 경우 브라우저가 확인 번호로 완료 여부만 조회한다. 서버 삭제가 확인된 뒤에만 기존 `clearWithdrawnAccount`로 해당 계정의 브라우저 기록·초안·첨부·백업을 정리한다. 다른 계정으로 로그인한 경우 그 계정은 로그아웃하거나 정리하지 않는다. 로컬 정리가 실패하면 확인 번호와 재시도 경로를 유지한다.

공개 클라이언트는 최대20개 요청을 이어 처리하고, 이후에는 명시적인 재시도를 제공한다. 다른 기기는 저장된 서버 진행 상태를 읽어 원래 확인 번호를 받은 뒤 다음 요청에서 이어간다. 진행이 시작된 뒤에는 일부 파일이 이미 삭제됐을 수 있으므로 취소를 전체 원복으로 표현하지 않는다. 다른 기기의 로컬 초안과 이미 내려받은 파일은 해당 기기에서 별도로 정리한다.

운영 DB에는 `resumable_account_withdrawal`(20261002201347)을 적용하고, `study-command` v35 ACTIVE와 정확한 소스 일치를 확인했다. 새 보조 RPC는 service_role만 실행하며, 두 테이블은 RLS를 켜고 클라이언트 읽기를 허용하지 않는다. 기존 v34의 조건부 조회·요청 크기 제한·원문 코덱·사진 목차·명령 목록을 유지하면서 세 개념 컬렉션 초기화와 탈퇴 부분만 조합한다. 원본은 `production-base.js`, 재현 절차는 `scripts/build-study-command-production.mjs`이다. 운영 최신본이 바뀌면 원본 해시 검사에서 멈추고 새로운 판본을 대조한다.

관련 검사는 `account-withdrawal.test.ts`, `withdrawal-recovery.test.ts`, `production-command.test.ts`, `supabase-sync.test.ts`, `account-settings.test.tsx`이다. 파일 실패·50개 초과·소유권·마지막 관리자·재승인·최종 응답 유실·다른 계정 전환과 기존 원문 보존을 확인한다. 운영 직접 시험과 최종 공개·패키지 근거는 담당 작업의 `work/final-integration/` 및 프로젝트의 최신 마감 보고에 남긴다. 코드/모의 실패/실제 운영 서버/브라우저/물리 기기 확인을 구별한다.

기존 방법은 [Supabase 계정 삭제](https://supabase.com/docs/guides/auth/managing-user-data)와 [Storage remove](https://supabase.com/docs/reference/javascript/storage-from-remove)를 재사용한다. Storage 정리 후 계정 삭제는 제품 제약이며, 진행 상태와 임의 번호로 응답 유실을 복구하는 부분은 이 프로젝트의 구현이다.
