# 일정·과제·온라인 강의 관리

2026-10-01 사용자 요청 ‘그럼 다 구현해’에 따른 현재 구현이다. 화면은 `#/schedules`이며 ‘일정·과제’ 메뉴와 ‘다음 공부’의 기존 일정 편집기에서 같은 학습 계획을 사용한다. 화면과 저장·서버 검증 코드를 연결했으며 운영 적용·실제 기기 알림 수신은 별도 단계다.

## 현재 동작과 보존

- 월 달력·날짜별 목록·가까운 기한 순 정렬·일주일 안/기한 지남/기한 미정 요약, 이름·메모·해야 할 일·과목 검색, 종류/진행/보관/휴지통 필터를 제공한다. 20개씩 펼치며 보기·필터·월은 계정/namespace별 이 기기에 유지한다. 일정 원장과 구별하며 보기 설정의 다기기 동기화를 주장하지 않는다.
- 시험·퀴즈의 응시 확인, 과제 준비/제출, 온라인 강의 재생/학습/출석 확인, 주차별 강의 학습/출석 확인을 각각 남긴다. 필기·메모 확인은 선택해서 추가한다. 재생·필기·공지 확인을 출석 인정·독립 수행·숙달로 자동 해석하지 않는다. 보관도 완료로 바꾸지 않는다.
- 시작 가능일/시각, 기한/시각, 성적 비중, 원문 메모, 해야 할 일, 공지·강의 주소, 주차·관련 주제 범위를 저장한다. 날짜와 시각은 선택이다. 날짜만 알 때 저장 시각은 비워 두고 집계 계산에서만 한국 날짜의 끝을 사용한다. 기한 미정은 실패나 0으로 바꾸지 않으며 공지 확인일을 별도로 지정할 수 있다. 과목 공지를 실제로 확인한 시각도 독립 기록이다.
- 반복 마지막 날을 명시하면 시작 가능일 또는 기한부터 매주 독립 ID로 만든다. 마지막 날은 기준일에서 1년 이내이며 각 회차는 별도 수행 상태를 갖는다. 앞 주차 완료를 다음 주차로 복제하지 않는다. 각 회차의 수정·보관·복원은 독립 조작이다.
- 내용·기한·상태 수정, 보관, 휴지통 이동과 복원에서 이전 원문과 상태를 변경 이력에 보존한다. 마지막 변경 또는 특정 이전 기록으로 되돌릴 때 현재 내용도 새 이력으로 남긴다. 영구 삭제는 제공하지 않는다.
- 일정 초안은 닫기·재접속 후 다시 열린다. 기존 저장 키와 이전 초안 형태를 유지하며 반복 설정·편집 기준을 추가한다. 다른 창의 초안을 자동 덮어쓰지 않고 현재 저장 내용이 바뀌면 비교 후 명시적으로 반영하도록 한다. 저장 실패에서 입력과 초안을 유지한다.
- 서버 저장은 기존 `saveLearningPlan` 명령과 원장/operation/sequence 경로를 사용한다. 새 속성은 선택 속성이다. 기존 일정의 ID·원문·상태·초안을 새 상태로 일괄 환산하지 않는다. 새 kind `class`와 이력·공지 확인 기록은 서버에서도 검증하므로 프론트엔드와 study-command를 함께 적용해야 한다.

## 오전 9시 알림과 캘린더

앱 안의 오늘 확인할 일정은 한국 시간 기준이며 기한이 오늘~7일 뒤인 일정을 모은다. 제출 완료인 과제의 제출 기한과 출석 확인 완료인 강의의 출석 기한은 알림에서 제외하되 다른 수행 상태는 그대로 남는다. 휴지통·보관 일정과 삭제 과목은 발송 대상에서 제외한다. 기한 미정은 지정한 공지 확인일이 되면 확인 대상으로 남는다.

기기 알림은 승인된 개인 계정이 직접 허용한 기기에 한해 Web Push를 사용한다. 알림을 켤 때 대기 기록의 서버 저장을 먼저 완료한다. 서버는 Auth에서 사용자를 정하고 본문의 사용자 ID를 신뢰하지 않는다. 일반 계정도 자신의 일정 알림을 쓸 수 있으며 AI 권한과 별개다. 로그아웃은 해당 기기 구독을 끈다. 구독 주소/키는 서버 전용 테이블에 보관하며 일반 client role은 직접 접근할 수 없다. 계정 삭제 시 구독은 FK cascade로 정리된다.

알림은 하루 한 묶음이다. 한 번의 cron 실행에서 최대10기기, 기기당 하루 최대12시도와 3분 claim lease를 둔다. 오전9시 한 시간 동안 매분 미처리 기기와 실패를 재시도하며 성공·대상 없음은 당일 처리 완료로 남긴다. 만료404/410는 비활성화하고 하루 tag/topic으로 같은 알림 교체를 사용한다. 공급자 접수 후 저장 응답 실패 같은 조건의 재발송 가능성까지 정확히 한 번 전달을 보장하지는 않는다. 승인 해제 시 발송하지 않는다. 하루 알림 본문에는 일정 이름과 기한만 포함하고 원문 메모·공지 주소는 전송하지 않는다.

캘린더 파일은 RFC5545의 날짜/시각 구분·고정 UID·수정 SEQUENCE·UTF-8 75octet folding·CRLF·TEXT escape를 사용한다. 일주일 전부터 오전9시 묶음 DISPLAY 알림을 포함한다. 파일은 내보낸 시점의 사본이며 지속 구독이나 자동 갱신이 아니다. 캘린더 앱이 가져오기/알림을 처리하는지는 해당 앱에서 확인해야 한다. 제어 문자·고립 surrogate는 내보낸 파일에서 읽을 수 있는 `\uXXXX`로 표시하되 앱의 원문은 그대로 보존한다.

## 채택한 기존 방법과 근거

기존 공통 Input/Select/Modal·토큰·학습 계획 저장·승인된 계정의 Supabase client를 재사용했다. 일정 규칙은 순수 domain 함수, 기기/파일/저장은 data, 화면은 ui, 승인/발송은 server로 나눴다. 새로운 캘린더 라이브러리는 앱 번들에 추가하지 않았고 독립 `ical.js 2.2.1` 파서로 출력 호환성을 확인했다.

- [RFC5545](https://www.rfc-editor.org/rfc/rfc5545.html): 캘린더 사본과 VALARM 형식. 일정 관리의 학습 효과를 보장하는 표준이 아니다.
- [Apple Web Push 안내](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [WebKit iOS/iPadOS 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/): 사용자의 직접 허용과 홈 화면 웹앱 조건. 실제 기기에서의 수신을 문서 확인으로 대체하지 않는다.
- [Supabase 예약 함수](https://supabase.com/docs/guides/functions/schedule-functions): pg_cron/pg_net/Vault를 이용한 서버 예약. 운영 비밀은 소스에 넣지 않는다.
- [공식 web-push](https://github.com/web-push-libs/web-push): 서버에서 암호화/VAPID 발송에 `npm:web-push@3.6.7`을 사용한다. React 화면에는 이 서버 라이브러리를 넣지 않는다.
- React 검사 기준은 기존 hook·effect cleanup·안정적인 notification port·버전 있는 로컬 보기 설정·지연 로딩·접근 가능한 실제 입력 요소의 점검에 적용했다. 성능/접근성 전체 준수로 확대하지 않는다.

## 운영 적용 순서

현재 소스와 생성된 함수 bundle이 준비되었으며 이 작업에서 새 DB·알림 함수·키·cron이나 공개 프론트엔드는 운영에 적용하지 않았다. 새 계정/결제/사용자 자료 업로드도 수행하지 않았다.

1. 현재 병행 변경을 보존해 프론트엔드와 기존 study-command의 변경을 합친 검증 사본을 만든다. `npm run build:backend`와 앱 build를 실행한다.
2. 기존 운영 DB와 migration 상태를 대조한 뒤 추가 migration `supabase/migrations/20261001064004_schedule_notifications.sql`만 적용한다. 기존 migration 번호가 저장소와 다르게 정리된 조건에서 전체 `db push`를 무조건 실행하지 않는다.
3. 공식 web-push로 VAPID key pair를 로컬에서 생성하고 private key를 노출하지 않고 Supabase secrets에 `STUDY_PUSH_PUBLIC_KEY`, `STUDY_PUSH_PRIVATE_KEY`, `STUDY_PUSH_SUBJECT`(유효한 https 주소 또는 mailto), 32자 이상의 `STUDY_PUSH_CRON_SECRET`을 넣는다. 기기 구독을 위해 public key만 인증된 config 응답으로 반환한다.
4. study-notifications와 study-command의 통합 bundle, 앱/manifest/service worker를 기존 허용 대상에 적용한다. 실제 승인 시험 계정의 등록/상태/해제·잘못된 token/다른 계정·일반 계정의 dispatch 거부를 확인한다.
5. Vault에 `study_push_project_url`, `study_push_publishable_key`, `study_push_cron_secret`을 등록하고 `supabase/operations/schedule-notifications-cron.sql`을 실행한다. subject/private key/cron secret을 프론트엔드 환경 변수나 문서에 넣지 않는다.
6. Safari에서 홈 화면에 추가해 연 앱에서 실제 알림을 허용하고 오전9시 수신·알림 클릭의 개인 일정 진입·해제를 확인한다. 새 설정은 사용자에게 직접 알림을 켜기 전 자동 구독하지 않는다.

운영 적용 승인과 접근 조건은 현재 프로젝트의 배포 지침을 따른다. 기존 키/승인 권한/다른 서버 함수와 원장은 보존한다.

## 확인한 범위

정상 의존성의 격리 사본에서 관련9파일28검사, 타입 포함 앱 build, backend build와 디자인 검사(오류0)를 통과했다. PGlite의 PostgreSQL에서 실제 SQL/명령 처리로 원문·NUL·고립 surrogate·CRLF·시각·이력의 왕복, 중복 operation과 stale sequence 거부를 확인했다. 알림 서버의 발송은 합성이며 외부 provider로 실제 발송하지 않았다.

빌드된 localhost 화면에서 합성 일정의 입력→저장→재접속, 닫고 재열기, 주차별 반복, 독립 상태, 휴지통→복원, 기한 미정 필터/공지 확인일/필기 확인, 공지 확인 기록과 좁은 화면을 직접 확인했다. 물리 iPad/iPhone·IME·VoiceOver·다기기 Sync·실제 오전9시 수신·장기 학습 효과는 미검증이다. 상세 로그·그림은 프로젝트 `outputs/20261001-schedule-management/`에 있다.

## 추가 개발과 검증의 구분

기본 일정·과제·온라인 강의 관리는 기존 학습 계획 저장, 명시적 상태 입력, RFC 5545 파일과 표준 Web Push를 재사용한다. 새로운 학습 이론을 만들어야 성립하는 기능은 아니다.

- 실제 iPhone/iPad의 홈 화면 앱에서 권한 허용→오전9시 수신→알림 클릭→해제를 확인하는 것은 운영 검증이다. 합의한 다섯 WebKit 화면 환경의 시험으로 물리 기기 수신·한글 IME·VoiceOver를 대신하지 않는다.
- 학기들이 쌓였을 때 긴 원문·변경 이력을 포함한 저장 크기와 입력 지연을 측정하고 필요할 때 이력 조회·저장을 나누는 것은 후속 성능 개발이다. 첫 구현은 검색/필터·20개씩 표시·초안 보관·삭제 복구를 갖추며 이력을 임의로 버리지 않는다.
- 학교 LMS의 공지·과제·출석 자동 수집은 조건부 연동 개발이다. 해당 학교의 공식 API·인증·권한·개인정보 조건과 공지 변경의 의미를 조사한 뒤 별도로 구현한다. 현재 수동 입력/공지 주소 저장을 자동 수집으로 보고하지 않는다.
- Apple/Google 캘린더의 실시간 양방향 동기화도 조건부 연동 개발이다. 현재 .ics는 내보낸 시점의 복사본이며 이후 기한 변경은 새 파일을 내보내야 한다. 외부 계정 권한, 중복·삭제·시간대와 충돌 보존을 별도로 설계해야 한다.

2026-10-01 운영 DB의 추가 스키마·알림 서버·VAPID 서버 secrets·09시(KST) 예약 실행을 적용했다. 승인된 합성 시험 계정 둘의 실제 HTTP 호출 16개에서 원문/NUL/surrogate/CRLF·변경 이력·공지 확인 기록의 왕복, 중복 저장, 타 계정 거부/격리, 알림 설정·구독·해제를 확인했다. 실제 기기 push를 발송하지 않았다. 공개 앱 적용 및 CI 결과는 해당 배포 보고에서 별도로 기록한다.


운영 예약 실행의 pg_net은 Supabase 관리 확장으로, 설치 schema 표시(public)에 대한 advisor 경고가 있다. 확장 소유자는 supabase_admin이고 postgres 배포 역할로 다른 grantor의 권한을 회수할 수 없어 회수 시도는 효과가 없었다. 이를 권한 변경 완료로 보고하지 않는다. 일반 계정 둘의 실제 REST 요청에서 net schema는 노출되지 않아 406/PGRST106으로 거부됨을 확인했다. 일정 구독 테이블과 일정 알림 RPC는 서비스 전용이며 사용자 요청은 인증한 서버 함수에서만 처리한다. 안내: https://supabase.com/docs/guides/database/database-linter?lint=0014_extension_in_public
