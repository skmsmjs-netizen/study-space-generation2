# 묶음 저장과 응답 유실 복구 — 2026-10-01

기존16개 명령 묶음은 항목마다 전체 원장을 압축하고 DB 응답을 다시 풀어 실제 누적 자료에서 HTTP546으로 중단됐다. 이제 명령을 순서대로 검증한 뒤 마지막 원장을 한 번 압축하고 승인 검사·공간 잠금이 있는 study_commit_batch RPC의 단일 트랜잭션으로 저장한다. 항목별 원래 opId·sequence·revision·중간 편집 이력을 유지한다. 잘못된 뒤쪽 명령/승인 거부/충돌은 전체 신규 묶음을 저장하지 않는다. 기존 단일 명령 RPC·원장 형식·키와 자료는 바꾸지 않는다.

앱은 전송 실패 뒤 다음 저장 재시도에서 서버를 먼저 확인한다. 정확한 요청 내용이 일치하는 저장 확인만 미전송 목록에서 제외하고 남은 명령을 재생한다. 다른 기기 변경이 끼어 있으면 두 사본을 보존하고 기존 충돌 경로를 유지한다. 응답 유실을 성공으로 꾸미거나 오프라인에 무한 재시도하지 않는다.

기준은 프로젝트 데이터 계약·책임 분리·기존 요청 확인/이력 모델과 PostgreSQL 원자적 트랜잭션이다. Supabase 공식 [실행 한도](https://supabase.com/docs/guides/functions/limits)의 CPU 제한을 확인해 반복 압축과 왕복을 줄였다. 플랫폼 한도를 변경하거나 무제한 규모 통과를 주장하지 않는다.
