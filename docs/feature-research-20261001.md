# 추가된 학습 기능의 연결·수리 엔진·추가 기능 연구

2026-10-01 · 사용자 요청: “추가 기능 연구는 필요없는가? 지금 많은 기능들이 추가되었는데.” → “어해라”

## 1. 연구 결론

현재 우선순위는 **이미 남긴 답변과 결과를 다시 쓰지 않고 다음 공부에 연결하는 기능**이다. 공부 기록·주제 카드·시험 연습·코딩 연습은 서로 다른 목적과 결과를 갖는다. 개발 중인 암기시험·강의 자료까지 같은 화면과 계산에 넣으려면 원자료 연결, 평가 의미, 복습 대상을 먼저 정해야 한다. 사용자가 실제로 혼란을 겪었다거나 학습 효과가 저하됐다는 판단은 하지 않았다.

추천 순서는 ① 기존 답안에서 수행 확인으로 이어 가기 ② 오늘의 복습·기한·자유 공부를 함께 보여주기 ③ 검토한 자료 카드를 재사용하기 ④ 코딩 예제의 선택 주제 연결이다. 일정 알림과 음성 원본의 다른 기기 보관은 기존 요구를 완성할 별도 개발 범위로 유지한다. 새 개인 능력·흥미·성적 종합 점수는 필요한 관측과 타당성이 아직 정해지지 않았다.

이 문서는 기능 연구와 실행안이다. 새 기능 채택·제품 코드 수정·운영 배포·개인자료 외부 전송·알림 예약은 수행하지 않았다. 기존 기능·원문·ID·초안·사용자 배치는 유지했다.

## 2. 확인 범위와 시점

- 활성 공통 지침, `AGENTS.md`, 최신 인계, 제품 결정, 기본 지침의 기능 추천 기준, 실제 App 경로·자료형·저장 호출·통계·추천 계산을 대조했다. `study-review`의 실제 호출 경로와 보존 기준을 적용했다.
- 공개 저장소의 확인 기준은 `origin/main` **3aff1c4121e602050784790ba2cee6fe38047ec9**이다. `git fetch origin main`으로 확인했다. 이는 배포 자산 일치·화면 직접 조작을 새로 확인했다는 뜻이 아니다.
- 공용 개발본은 확인 시작 시 HEAD **9ca470c6be8127bddd2008b8e156c63ad4f33342**, 다수 미커밋·미추적 파일이 있는 상태였다. 연구 중에도 다른 작업이 바뀌므로 아래 경로와 함수명이 근거다. 공용 HEAD/index를 바꾸거나 다른 작업을 되돌리지 않았다.
- 공개 main에는 코딩 연습이 연결되어 있다. 최신 인계는 온라인 컴파일·개인 저장의 운영 왕복과 배포 증거를 남긴다. 이전 대화의 ‘로컬 구현만 있음’ 판단은 이 최신 상태로 수정한다.
- 암기시험·강의 자료·그래프뷰·칸반보드는 확인 시 공용 개발본에서 읽었다. 위 공개 main의 App·모델에는 연결되지 않았다. 이 차이는 개발·공개 상태 차이이며 미구현 단정이나 해당 기능의 불필요 판정이 아니다.
- 종료 전 최신 인계에 추가된 ‘그래프뷰·칸반보드 개발본 구현’을 확인했다. 두 보기는 사용자의 새 명시 요청으로 채택되었으므로 이전 ‘별도 연결 지도 없음’ 결정을 이 보기의 금지로 적용하지 않는다. 개발본 직접 조작/저장 증거와 운영 미배포/서버 연결 잔여를 구분해 유지한다.
- 사용자의 실제 계정·답변·음성·공부 기록을 연구용 표본으로 읽거나 복제하지 않았다. 물리 기기, 실제 학습 효과, 전체 제품 QA는 이번 확인 범위 밖이다.

## 4. 연결이 끊기는 지점과 이미 해결된 부분

### F1. 답안은 남았지만 다음 공부에 쓰려면 다른 곳에서 결과를 다시 남긴다

`domain/recommendation-workspace.ts`의 `recommendationInput()`은 목표·일정·`workspace.events`와 관련 StudyRecord 활동을 읽는다. `domain/statistics.ts`의 `statistics()`도 StudyRecord와 `workspace.events`를 읽는다. RecallCard의 review, MemoryTest의 판정, 시험 연습 QuickMemo, CodeExample 실행 결과는 이 수행 사건 입력에 자동으로 들어가지 않는다.

주제 카드의 `reviewRecallCard`는 기억 예약과 선택 메모를 저장한다. 시험 연습의 `savePracticeMemo()`는 기존 `saveMemo`를 쓴다. 암기시험의 `saveMemoryAttempt()`는 `saveMemoryTest`를 쓴다. 다음 공부의 `saveResponse()`에서 수행 사건을 별도로 남긴다. 따라서 답안이 있어도 다음 공부가 읽는 수행 근거가 따로 생기는 구조다.

이 분리는 부정확한 자동 성공 환산을 막는 올바른 경계다. 개선할 대상은 **답안과 판정을 다시 입력하는 부담 및 원자료 참조 부족**이다. 같은 주제라는 이유만으로 기존 목표를 자동 선택하거나 FSRS ‘쉬움’을 목표 pass로 변환하는 설계는 제외한다.

### F2. 오늘의 복습 예약과 다음 공부가 서로 다른 후보 체계다

`recallQueue()`는 FSRS due/learning 상태와 하루 새 주제 한도를 쓴다. `nextStudy()`는 목표 상태·일정·조건을 쓴다. 현재 다음 공부 입력에는 RecallCard가 없다. 같은 주제를 두 영역에서 만날 수 있지만, 서로 목적이 다르므로 무조건 하나의 할 일/점수로 합칠 수 없다.

제안은 오늘 화면에서 ‘예약 복습’, ‘기한 있는 일’, ‘원하는 주제’를 이유와 함께 보여주고 **한 번에 선택하는 행동 수를 줄이는 것**이다. 같은 주제에 두 근거가 있으면 주제 표시만 묶고 선택 가능한 행동/근거는 유지한다. 기록을 하면 복습/과제 상태까지 자동 완료시키지 않는다.

### F3. 카드가 세 종류지만 질문·답안·평가 단위가 다르다

- 주제 카드: 주제 이름을 보고 주제 전체를 떠올리며, 주제당 기억 상태를 저장한다.
- 암기 항목: 사용자가 질문과 기준 답안을 등록한다. 시험에서 응답과 직접 비교 판정을 남긴다.
- 자료 카드: 생성 결과 내부의 질문/답안과 sourceIds를 갖는다. 제외/수정/원문 근거 열기는 있으나 현재 FSRS 예약/평가 저장은 연결되지 않았다.

질문 하나가 맞았다는 사실은 주제 전체를 떠올렸다는 사실과 다르다. 세 종류를 같은 카드로 자동 이관하지 않는다. 원자료/생성 버전이 있는 자료 카드를 검토 후 선택적으로 암기 항목으로 쓰는 연결은 조건부 후보다. 학습용 질문·답안과 원문 출처를 유지해야 한다.

### F4. 코딩 예제는 학습 주제와 구조적으로 연결되지 않는다

확인 시 `CodeExampleContent`에는 제목·언어·code·stdin·notes·lastRun이 있고 topicId는 없다. `currentCodeRun()`은 저장 출력이 현재 코드/언어/입력의 결과인지 검사한다. 실제 실행과 오래된 출력 구별은 이미 있으므로 같은 기능을 다시 만들지 않는다.

주제 상세에서 해당 예제를 열고 돌아오려면 선택 주제 참조가 필요하다. 자동 제목 유사도 매칭은 필요하지 않다. 예제 수정·실행·저장은 공부 체크나 수행 성공을 만들지 않는다. 통과/실패를 판단할 입력-예상출력 또는 실제 기준이 별도 등록되지 않았으므로 ‘실행 성공’을 정답으로 제시하지 않는다.

### F5. 메뉴가 늘어나는 부담은 현재 예상 위험이다

확인 시 공개 main의 공통 메뉴는 10개이고 개발본은 14개다. 실제 사용자의 선택 실패를 측정한 값은 아니다. 공개 메뉴에 개발 기능을 모두 같은 수준으로 추가하면 목적을 구분해야 하는 부담이 커질 수 있다.

수정 후보는 평소 기록/복습을 쉽게 열고, 주제 상세 안에서 ‘시험처럼 풀기/암기 항목/관련 예제’를 상황에 맞게 찾도록 하는 것이다. 기존 기능 삭제나 사용자 배치 재설정은 하지 않는다. 적절한 첫 화면/추가 보기 구분은 실제 빈도와 과제 수행으로 확인해야 한다. [Nielsen의 단계적 기능 노출 기준](https://www.nngroup.com/articles/progressive-disclosure/)은 드문 기능을 다음 단계에 두되 자주 필요한 기능과 명확한 진입을 유지하라고 설명한다. 여기서 메뉴 재배치는 프로젝트에 대한 설계 추론이며 사용자 실험 결과가 아니다.

### 이미 해결된 부분은 유지한다

주제 카드의 평가 뜻 설명·예약/무작위 모드·건너뛰기·마지막 평가 되돌리기, 암기시험의 답 제출 전 기준 답안 숨김·직접 비교·틀림/부분 맞음 재시험, 자료 카드의 원문 근거·수정 전 문장, 코드 출력의 현재 소스 일치 검사, 시험 연습의 중단/복귀·원문 메모 저장은 실제 코드에 있다. 이들을 ‘새 기능’으로 다시 추천하지 않는다.

FSRS 공식 문서는 rating으로 기억 상태와 인출 가능성을 모델링한다. 여기서 카드의 difficulty는 학습자의 일반 능력 점수가 아니다. [FSRS 알고리즘](https://github.com/open-spaced-repetition/awesome-fsrs/wiki/The-Algorithm)

현재 `recallPreview()`는 ts-fsrs와 요청 유지율/간격/학습 단계 설정을 쓰며 개인 이력을 학습한 optimizer 경로는 이 함수에 없다. **평가 이력에 따라 카드 상태가 달라지는 것과 개인 파라미터를 학습한 것은 다르다.** 기본 유지율 0.9도 해당 사용자의 실제 성취 90%라는 관측이 아니다. Anki 문서는 높은 목표 유지율에 따른 복습량 증가, ‘떠올리지 못함’을 Hard로 평가하면 생기는 왜곡, optimizer의 이력 조건을 설명한다. 현재 앱의 평가 안내는 이 구별을 이미 제공하므로 유지한다. [Anki 공식 설정 안내](https://docs.ankiweb.net/deck-options.html#fsrs)

인출 연습과 간격을 둔 공부는 연구 검토에서 폭넓은 유용성이 보고됐다. 다만 연구는 자료·학습 조건·평가 과제를 나누어 판단한다. 이를 이 앱의 정확한 복습일, 특정 사용자 효과, 새로운 문제 해결이나 A+ 성적의 증거로 사용할 수 없다. [Dunlosky 등, 2013, 연구 검토](https://www.psychologicalscience.org/journals/pspi/1529100612453266/)

인출의 효과가 새로운 상황으로 옮겨가는 정도도 조건에 따라 달라진다. Pan·Rickard의 메타분석은 긍정적인 전이 가능성과 함께 최초 수행·응답 일치·확장된 인출 등의 조절 조건을 보고한다. 따라서 앱의 같은 카드 재시험과 새로운 문제의 독립 수행을 따로 관측하는 판단이 타당하다. 이는 ‘인출은 암기에만 도움이 된다’는 주장도, 어떤 카드든 문제풀이 능력을 보장한다는 주장도 아니다. [Pan·Rickard, 2018, 원논문](https://pdf.retrievalpractice.org/transfer/Pan_Rickard_2018.pdf)

수리 모형 확대의 첫 목적은 ‘더 높은 점수’를 만드는 것이 아니라 **어떤 행동 후보를 바꿀지 정하는 것**이다. 새 관측이 후보 선택을 개선하지 못하거나 입력 부담만 늘면 점수/필드를 도입하지 않는다. 참고 생활 동역학 자료는 채택 미확정이라는 현재 README의 경계를 유지한다. 종료한 구현·옛 원본·과거 감사는 재열람하지 않았다.

## 6. 기능 후보와 실제 실행안

우선순위는 현재 코드의 연결 공백·기존 사용자 목적·새 입력 부담을 바탕으로 정했다. 사용 빈도나 효과를 실제로 측정한 순위가 아니다. 아래 후보는 이번 연구의 추천이며 자동 채택/배포 결정이 아니다.

### A. 기존 답안으로 수행 결과 남기기 — 먼저 연결할 후보

- **필요:** 시험 연습/암기시험의 답안을 보면서 다음 공부의 확인 결과를 남길 때 같은 글을 다시 쓰지 않게 한다.
- **대상 선택:** 현재 답안과 연결된 주제의 기존 확인 목표만 후보로 제시한다. 사용자가 목표를 고른다. 목표가 없으면 답안 저장만 마치고 목표 추가는 선택이다.
- **흐름:** 결과 화면 → ‘이 답안으로 확인 결과 남기기’ → 원답안 보기·기존 목표 선택 → 도움 여부/결과 등 아직 모르는 조건만 확인 → 수행 사건 저장 → 해당 다음 공부에서 근거와 원답안 다시 열기.
- **보존/계산:** 원문은 원래 Memo/MemoryTest에 둔다. 수행 사건은 source kind/ID/version/문항 참조와 당시 필요한 사본/판정 조건을 보존한다. 한 응시에서 여러 주제/문항이 있으면 연결 범위를 명시한다. 재시도·수정·판정 취소가 중복 성공 횟수를 만들지 않아야 한다.
- **부담/작은 대안:** 기존 결과 입력은 그대로 사용 가능하다. 결과 연결은 선택이며 시험 종료나 평소 기록의 새 필수 절차가 아니다. FSRS 네 단계 평가는 직접 pass로 매핑하지 않는다.
- **완료 기준:** 답안을 다시 쓰지 않고 수행 결과를 남길 수 있고, 새로고침 후 원답안/당시 기준을 열 수 있어야 한다. 도움/새 문항/간격 미확정·미응답·부분 판정이 성공으로 바뀌지 않으며 원답안 수정과 수행 판정 수정의 이력을 유지한다.

수행 사건의 참조 계약에는 `sourceKind`, `sourceId`, `sourceVersion`, 선택 `sourceItemIds`, 명시 `targetId/goalId`, 원래 판정과 수행 판정을 구분하는 값이 필요하다. 소유권·실제 원자료/버전 존재·목표 범위 일치·재시도 operation ID를 검사한다. 시험 응시 시각은 해당 응시의 관측이며 앱 밖 문제풀이 시각으로 일반화하지 않는다. 부분 맞음은 원래 판정으로 보존하고 목표 pass/fail은 직접 고른 기준에 따라 별도 확인한다. 필수 조건이 확인되지 않으면 수행은 unknown으로 남겨도 원답안은 정상 저장된다. 이는 구현 전 계약 제안이며 현재 서버에 이 필드가 있다는 뜻이 아니다.

### B. 오늘의 복습·기한·자유 공부를 함께 고르기 — 함께 검토할 후보

- **필요:** 홈 다음 공부와 주제 카드 예약 사이를 오가며 오늘 시작할 행동을 선택해야 하는 구조를 보완한다.
- **대상 선택:** 실제 due 카드·열린 일정·기존 추천만 쓴다. 후보가 없으면 기존 주제 선택을 유지한다. 서로 다른 근거를 같은 점수로 합산하지 않는다.
- **흐름:** 오늘 → ‘예약 복습’ 또는 ‘기한 있는 일’의 한 행동 선택 → 원래 기능/같은 주제에서 시작 → 종료 후 오늘 복귀. 원래 목록 전체도 계속 열 수 있다.
- **보존/부담:** 원래 사용자 순서·보류·새 주제 한도·날짜 수동 지정·각 기능의 상태를 유지한다. 새 입력은 요구하지 않는다. 주제 표시는 묶어도 행동/이유는 삭제하지 않는다.
- **완료 기준:** 같은 주제에 복습/시험 근거가 함께 있어도 중복된 의무로 보이지 않고 원하는 행동을 고를 수 있어야 한다. 과제 준비 후 제출은 남고, 메모 저장 후 복습 평가 예약은 변하지 않는다. 날짜 변경·중지·되돌리기 후 후보가 정확히 갱신된다.

### C. 검토한 자료 카드를 암기시험에서 재사용하기 — 개발 기능 연결 후 조건부 후보

- **필요 가설:** 자료 카드가 이미 있으면 같은 질문/답안을 암기 항목으로 다시 등록하는 일을 줄일 수 있다. 실제 중복 입력 경험은 아직 확인하지 않았다.
- **대상 선택:** 사용자가 제외하지 않았고 원문 근거를 확인한 카드만 직접 선택한다. AI가 자동 채택하지 않는다. 자료가 주제에 연결되지 않았다면 필요한 주제 선택 한 번을 제공한다.
- **흐름:** 자료 카드 → 원문 대조·수정 → ‘암기 항목으로 사용’ → 질문/답안/주제 확인 → 기존 암기시험에서 사용 → 결과에서 생성 당시 원문 근거 열기.
- **보존/부담:** material/result/card/source ID와 당시 버전을 유지한다. 이후 자료 수정·재생성·카드 제외가 과거 시험 답안을 바꾸지 않는다. 새로 생성할 필요 없이 수동 카드도 그대로 쓴다.
- **선행 조건:** 자료·암기 항목의 실제 저장/재접속 경로와 소유권이 준비되어야 한다. Plus 추가 과금 없는 GPT 조건과 별개인 API 구성을 몰래 대체 경로로 채택하지 않는다.
- **완료 기준:** 같은 질문을 재입력하지 않고 시험할 수 있으며 잘못 생성된 카드의 수정/제외가 유지된다. 출처 ID가 실제 존재한다는 검사는 내용이 정확하다는 판정과 구별한다.

### D. 코딩 예제를 주제에 연결하기 — 사용 상황에 따른 조건부 후보

- **필요 가설:** 특정 과목/주제를 공부하며 같은 예제를 다시 여는 상황에 도움이 된다. 모든 코딩이 과목 공부라는 가정은 하지 않는다.
- **대상 선택/흐름:** 예제 저장 시 선택 주제 연결 → 해당 주제에서 관련 예제 열기 → 코드 실행/설명 수정 → 원래 주제로 복귀. 주제에 연결하지 않은 독립 예제도 유지한다.
- **보존/부담:** 기존 예제 ID/코드/표준 입력/출력/설명/이력을 유지하고 연결만 선택적으로 추가한다. 제목 유사도/실행 성공으로 관계·정답·공부 체크를 만들지 않는다.
- **완료 기준:** 주제 이름 수정 후 같은 예제가 열리고, 주제 휴지통 때 예제와 원문을 삭제하지 않는다. 이전 출력과 현재 소스 차이를 유지한다. 반복 실행을 독립 해결 횟수로 세지 않는다.

## 7. 기존 요구로 남는 개발과 보류하는 신규 방향

**일정 알림은 기존 요구의 구현 잔여다.** 현재 읽은 학습 일정 코드에는 시간/기한 목록이 있지만 앱을 닫은 뒤 발송·기기 구독 경로를 확인하지 못했다. 활성 소스/index에서 PushManager·serviceWorker·기기 알림 경로 검색은 연결 근거를 찾지 못했다. 단순 화면 토스트를 기기 알림으로 보고하지 않는다. iPhone/iPad의 Web Push는 홈 화면 웹앱·사용자 조작에 따른 권한 요청 등 조건이 있다. 따라서 앱 안 목록을 먼저 유지하고, 기기 알림 연결은 설치·허용·발송·변경/취소·중복/민감 본문 노출·실제 기기 수신을 확인하는 별도 작업으로 잡는다. 기존 오전9시 묶음 알림/일주일 내 마감 선호와 추가2시간 알림의 잠정성을 유지한다. 이 연구에서 알림이나 외부 일정은 생성하지 않았다. [WebKit 공식 Web Push 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

**음성 원본 다기기 보관은 기존 자료 기능의 부분 구현이다.** 현재 자료 계약은 metadata와 IndexedDB bytes를 나눈다. 다른 기기에서도 원음을 들으려면 계정 소유권·원본 bytes 업로드/재수신·hash 일치·오프라인·용량·복구·탈퇴/보관 범위를 연결해야 한다. metadata 동기화나 같은 파일 다시 가져오기 안내만으로 완료가 아니다.

**새 문제로의 확인은 별도 입력이 필요한 조건부 방향이다.** 기존 다음 공부는 같은/새 문항과 도움/간격 조건을 표현한다. 현재 일반 기록에는 문제 본문/번호가 없으므로 자동으로 ‘동일 원리의 새 문제’를 골랐다고 할 수 없다. 이미 등록된 암기 카드의 재시험은 같은 문항이며 전이 수행의 증거가 아니다. 현재는 사용자가 실제로 푼 문제의 원문/조건을 선택적으로 남기는 경로를 활용하고 자동 선정 엔진은 선행 연구가 더 필요하다.

다음은 이번 우선순위에 넣지 않는다.

- 모든 주제에 문제 번호·세부 개념·매일 상태·확신 점수를 요구하는 방식: 현재 입력 계약과 부담이 맞지 않는다.
- 기록량·코드 실행·AI 요약·카드 ‘쉬움’을 합친 능력/숙달/성적 종합 점수: 관측 의미와 검증이 부족하다.
- 제목 유사도나 목차 인접성으로 혼동·선행관계를 만드는 비교 추천: 대상 선정 근거가 없다.
- 이미 있는 틀림/부분 맞음 재시험, 카드 되돌리기, 최근 기록 표시, 원문 근거 열기를 신규 기능으로 다시 만들기: 기존 구현을 재사용한다.
- 기존 참조를 복제하는 또 다른 의미 지도·생활 동역학 입력·사고 도구의 필수 루틴화: 추가 필요나 채택 근거가 없다. 새로 채택한 그래프뷰·칸반보드는 유지한다. 그래프뷰의 탐색 배치와 Canvas의 개인 저장 좌표를 구별하며 새 보기를 이유로 기존 원문/배치를 다시 만들지 않는다.

## 8. 구현으로 옮길 때의 순서와 검증

1. **A의 자료 참조와 수행 판정 계약부터 확정한다.** 원자료 종류·버전·문항 범위·중복/취소를 먼저 정의하고, 공개 기능인 시험 연습→기존 수행 확인 한 경로부터 구현한다. 암기시험/자료 카드 전체 공개를 선행조건으로 강제하지 않는다.
2. **B는 기존 후보를 보여주는 홈 연결로 작게 시작한다.** 새 수리 종합 점수 없이 예약 복습 진입·선택/복귀를 연결한다. 메뉴 전체 개편은 실제 관련 흐름 확인 뒤 판단한다.
3. **C는 자료·암기시험의 실제 저장 연결 후 진행한다.** A를 재사용하며 카드 원문/출처/시험 사본을 보존한다. AI 호출을 완료 조건으로 강제하지 않고 수동 자료로도 연결을 확인한다.
4. **D와 기존 알림/음성 저장 잔여는 목적에 따라 별도 진행한다.** 앞 세 후보를 완료하면 전체 제품이 끝난다고 보고하지 않는다. 사고 도구·GPT·전체 능력 모형의 미정 조건도 그대로 남는다.

기능 완성은 합성 자료의 자동 확인 → 같은 코드의 직접 조작·저장·재열기 → 허용된 서버/공개 연결 중 바뀐 범위 확인으로 판정한다. 기존 사용자 원장을 시험하지 않는다. 실제 기기와 학습 효과는 실행한 근거가 있는 경우에만 별도로 보고한다. 메뉴 선택 시간/중복 입력 횟수/원자료 복귀 성공은 사용성 확인이고, 지연·새 문항의 독립 수행은 학습 수행 확인이다. 두 결과를 같은 ‘효과’로 묶지 않는다.

## 10. 합성 자료로 직접 확인한 계산 경계

공용 개발본의 실제 도메인 함수들을 esbuild로 묶어 Node에서 실행했다. 가상 과목·주제·공부 기록 한 건만 만든 메모리 내 자료이며 사용자 계정/원장/브라우저 저장/외부 API는 사용하지 않았다. 재현 스크립트는 `work/feature-research-20261001/probe.ts`, 결과는 `work/feature-research-20261001/evidence.json`이다.

| 실행한 경우 | 확인 결과 | 연구에서의 의미 |
| --- | --- | --- |
| 기존 공부 기록에 FSRS 쉬움 평가·시험 연습 메모·맞음 판정 암기시험·성공 실행 예제를 추가 | 여덟 지표 동일, 다음 공부 `activity_only` 유지 | 새 기능의 저장이 현재 수행 성공 입력에 자동 합류하지 않음을 재현했다. 자동 성공 환산 방지와 연결 공백을 함께 확인했다. |
| 직접 명시한 도움 없음·새 문항 pass 수행 사건 추가 | 독립 성공 1회, 목표 `confirmed` | 현재 엔진은 필요한 근거를 명시한 사건으로 판단한다. |
| 같은 수행 사건의 도움 여부를 unknown으로 변경 | 독립 성공 0회, `confirmed` 아님 | 입력이 빠진 경우 성공을 꾸미지 않는다. |
| 맞음·부분 맞음·미응답 미판정 문항을 각각 요약 | correct 1 / partial 1 / unassessed 1, wrong 0 | 부분/미응답을 실패나 0점으로 바꾸지 않는다. |
| 응답 없는 문항에 wrong을 부여 | 검증 함수가 거부 | 미응답과 오답을 구별한다. |
| 저장 출력 뒤 코드 본문만 변경 | currentCodeRun true→false | 이전 출력과 현재 소스 결과를 구별한다. |

선택한 여섯 확인은 통과했다. 이 실험은 코드의 자료 소비/판정 경계 확인이다. 화면 조작·운영 서버·공개 배포·기기 알림·학습 효과를 새로 확인한 증거는 아니다. 제품 코드를 바꾸지 않았으므로 전체 빌드/QA를 반복하지 않았다.
