## 운영 탈퇴의 실제 확인

운영 계정 두 개를 새로 만든 합성 자료만 사용했다. 첫 계정의 첨부51개를 올리고 첫50개를 정리한 뒤 중단했다. 재로그인 상태에서 `withdrawalPending`과 suspended를 확인했고, 이 계정의 자료 조회·새 업로드 거부 및 두 번째 계정 파일1개의 보존을 확인했다.

새 브라우저에서 남은 정리를 이어 갔다. 실제 서버가 마지막 파일과 계정을 삭제한 응답을 끊어 결과 유실을 유도했으며, 완료 확인표로 성공을 복구했다. 다른 창의 보존 잠금으로 첫 기기 정리를 실패시켰고, 확인표가 유지되는 것과 새로고침 후 기기 원장/확인표의 최종 정리를 확인했다. 두 번째 계정도 정식 탈퇴 경로로 정리했다. 마지막 DB 조회에서 해당 두 계정0개, Storage 객체0개, 관련10개 테이블의 계정 행0개였으며, 시험 완료표도 확인 후 해당 두 개만 삭제했다. 기존 개인 계정·공부 원문은 시험 대상으로 사용하지 않았다.

운영 migration: `20261002201347_resumable_account_withdrawal.sql`. 완료 확인표는 계정/공부 내용을 저장하지 않는다. RLS와 서비스 전용 RPC, 마지막 유효 관리자 보호, 탈퇴 중 관리자 재승인·동시 업로드·다른 파일 소유권을 관련 SQL 회귀로 확인했다. 파일은 Storage API로 지우며, Storage 메타데이터만 직접 삭제하지 않는다. 이 순서는 [Supabase 사용자 삭제 지침](https://supabase.com/docs/guides/auth/managing-user-data#deleting-users)과 [Storage remove API](https://supabase.com/docs/reference/javascript/storage-from-remove)에 따른다.

운영 v35 읽기 회수본은 후보와 정확히 일치한다. SHA-256: `235f963b16c7fc2abc767c18d14c54710b8bee5a3ba6b8afe24d2b4cb5368409`. v34의 조건부 조회·본문 크기 제한·지원 명령·직렬화·사진 목차 경로를 보존했고, 새 계정 기능을 운영 최초 저장 보수와 함께 연결했다.
