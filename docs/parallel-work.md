## 반복 사용

1. 작업 시작에 관련 기존 이슈·현재 인계·소스를 확인하고 요청 범위, 변경 파일, 원래 대화 ID, 완료 조건과 다음 판단을 남긴다. 같은 결함의 이슈를 중복 생성하지 않는다.
2. 공유 파일/공통 결함은 기존 통합 수정을 먼저 재사용한다. 다른 대화가 수정 중인 구간은 겹침을 기록하고 필요한 부분만 수정한다. 파일 잠금·원격 담당 배정·대화 전달을 자동 수행했다고 보고하지 않는다.
3. 구현/검증/공개 반영 단계가 바뀌면 실제 커밋·CI 링크와 확인 범위·직접 남은 조건을 갱신한다. 로컬 구현 완료와 공개 적용·실제 서버 쓰기·물리기기 증거를 구별한다.
4. 요청받은 배포에서 자신의 변경이 최신 후보에 포함됐는지 확인하고 통합 실행을 추적한다. 재실행/취소는 대체본의 변경 포함과 기존 결과를 확인한 뒤 기존 허용 범위에서 한다.
5. 완료/중단/재개는 기존 이슈를 갱신하며 이력·원문·ID·설정/개인 배치를 보존한다. 자동 예약/감시/대화 전달·새 배포 권한을 만들지 않는다. 접근 불가일 때 다른 허용된 작업과 로컬 인계는 이어가고 그 연결 조건만 기록한다.

Linear는 실행 상태/의존성, GitHub는 코드·CI·배포 증거, 저장소 담당 문서는 요구·보존 계약/상세 기준을 담당한다. 공식 연결 도구의 조회/이슈/관계/프로젝트 문서를 사용했고 설치 수를 늘리지 않았다. 이 운영 연결은 자동 동기화나 파일 충돌 해결 시스템이 아니다. 개인 공부 내용/첨부 원문/인증정보를 Linear에 보내지 않는다. 일반 검사 범위·마감 정책은 [작업 진행과 검증 정책](../../docs/작업%20진행과%20검증%20정책.md)을 그대로 따른다.
