# 저장·동기화 호출과 대기 개선

2026-10-01 사용자 “그럼 뭐 지금 해봐” 요청의 첫 구현 범위입니다. 현재 저장 인터페이스와 원문/ID/이력/초안/충돌 보존을 유지하면서 반복 조회의 전송량과 연속 저장의 왕복을 줄였습니다. 첫 로컬 구현 뒤 사용자의 누락 점검·배포 요청에 따라 최신 공개 원본과 운영 서버를 보존해 배포를 진행했습니다. 아래 첫 구현의 측정은 당시 증거로 유지합니다.

## 채택한 방법과 실제 연결

기존 버전(sequence)을 사용하는 조건부 조회, 진행 중인 요청 공유, 순서를 지키는 제한된 묶음 전송, 명령 ID에 따른 재시도를 재사용했습니다. HTTP 캐시의 조건부 재검증 개념을 인증된 기존 POST 프로토콜에 적용한 프로젝트 구현이며 HTTP 304/공용 캐시가 아닙니다. 클라이언트는 `knownSequence`를 보내고 서버는 인증·현재 승인·소유권·전체 상태 검증 후 같은 버전에 `unchanged`와 사용자/공간/기능 정보를 응답합니다. 새 자료는 계속 전체 검증합니다. 변경 없는 응답만 이미 검증한 동일 base 객체를 재사용하며 로컬 편집 상태를 바꾸지 않습니다.

`syncCapabilities.batchCommands`를 서버가 명시했을 때만 대기 명령을 최대16개/본문 약200만 UTF-16 code units 범위로 전송합니다. 두 수치는 프로젝트의 보수적인 시작값이며 공인 성능 기준이 아닙니다. 전송을 모으기 위한 새 타이머는 없고 이미 대기 중인 명령만 묶습니다. 큰 단일 명령과 이전 서버는 기존 단건 경로를 사용합니다. 모든 중간 명령·ID·원문·이력은 유지하며 버전 순서를 지켜 실행합니다.

묶음 전체의 원자성을 주장하지 않습니다. 각 명령이 기존 PostgreSQL 트랜잭션으로 확정됩니다. 중간 DB/연결 실패는 이미 확정된 앞부분을 남길 수 있으며 클라이언트는 응답 확인 전 전체 명령을 보존합니다. 재시도는 같은 ID/내용을 검사하고 확정된 앞부분을 건너뜁니다. 재접속에서는 앞부분의 연속된 확인과 `server.sequence = base.sequence + 확인된 개수`가 일치하는 경우만 남은 명령을 이어갑니다. 다른 기기 변경이 섞였거나 순서가 맞지 않으면 기존 충돌 보관으로 양쪽을 유지합니다.

클라이언트의 `local-command`, `local-journal`, `sync-load`, `sync-execute`, `sync-batch` 시간을 메모리에 최대120개만 보관하고 Performance Timeline에는 종류별 최신 측정만 둡니다. `readRequestPerformance()`로 선택 확인할 수 있습니다. 원문/계정/토큰/ID/URL을 수집하거나 외부로 보내지 않으며 재접속 후 보관하지 않습니다. 서버는 요청별 `auth/access/read/validate/apply/commit/serialize/total`의 해당 시간만 `Server-Timing`에 제공합니다. 오류도 그대로 전달하며 계측 실패가 저장을 방해하지 않습니다. 서버 total은 핸들러 처리 시간이고 브라우저 왕복 시간·플랫폼 시작 대기를 포함하지 않습니다.

선정 근거: [MDN 조건부 캐시](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching), [Server-Timing](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Server-Timing), [web.dev INP](https://web.dev/articles/optimize-inp), [Supabase 쿼리 최적화](https://supabase.com/docs/guides/database/query-optimization). 새 라이브러리·스키마 이관·인증 완화 없이 기존 계약에 연결할 수 있어 선택했습니다.

## 지역 간 DB 왕복의 후속 보완

실제 HTTP 응답의 x-sb-edge-region에서 기본 실행은 ap-northeast-2, 프로젝트 DB는 ap-south-1임을 확인했습니다. [Supabase Regional Invocations](https://supabase.com/docs/guides/functions/regional-invocation)의 공식 SDK 옵션을 선택했고 현재 공개 프로젝트의2개 이상 묶음만 DB 지역으로 호출합니다. 일반 조회/단건과 다른 프로젝트의 환경 설정에는 강제하지 않습니다. 브라우저 preflight에 필요한 x-region 헤더를 기존 인증 CORS에 추가합니다. 인증/승인/소유권 검사는 그대로입니다.

합성 시험 계정의 실제 DB에서16개 묶음 교차 관측2회: 기본 서울5,352.99/5,038.05ms → DB 지역1,967.39/1,962.08ms. 각 요청의 명령16개와 이력은 유지됩니다. 따뜻한 변경 없는 조회는 기본719.53/727.63ms, DB 지역867.27/957.46ms이고 최초 DB지역 호출2,771.70ms라서 전 호출의 지역을 바꾸지 않았습니다. 서로 다른 명령과 증가하는 시험 원장을 사용한 관측이며 무작위 대조 실험·운영 사용자 체감 보장·모든 지역의 최적값으로 확대하지 않습니다.

운영 study-command v27은 직전 v26에서 CORS의 x-region 허용 한 곳만 추가해 병행 배포한 일정 도메인 변경을 보존했습니다. 회귀는3파일23개(지역 범위/다른 프로젝트/일반 조회·단건/브라우저 preflight/묶음 복구) 통과 후 fixture mock 타입을 명시해 전체 타입 검사와 맞췄습니다. 최종 배포 버전·CI·공개 사용 결과는 이번 작업의 최종 release evidence를 따릅니다.
